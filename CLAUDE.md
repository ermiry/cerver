# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Cerver is a C11 framework for building servers, built as a shared library (`bin/libcerver.so`). It supports five server types (`CERVER_TYPE_CUSTOM`, `GAME`, `WEB`, `FILES`, `BALANCER`), and a client API for connecting to cervers. The core (everything outside `http/`) is the one of the 1.8 line (branch `core`), ported in 2.0b-63, 2.0b-64 and 2.0b-66 (the whole 1.8: UDP, IPv6, the pools and workers, the portable 32 bytes header with the balancer's route id, the serializer by schema, the histograms and request handlers, game, zero warnings) and in 2.0b-70 (the 1.8.1: the fixes found while documenting the core, `examples/start.c`): `src/` and `include/` outside `http/` are identical to the ones of `core` except the web parts of `cerver.{h,c}` and `handler.{h,c}` (a web cerver never sends the cerver teardown packet into its HTTP connections), and fixes and features of the core land in `core` first and are seeded here. What `http` changed first in files of the core (`config.h`, `utils/base64.{h,c}`) goes back to `core` in the 1.8.2. The integration pairs run in IPv4 and in `::1` (`CERVER_TEST_ADDRESS`, `test/address.h`), new source files of the repo end with a newline. It targets Linux with gcc (uses `_GNU_SOURCE`, pthreads, OpenSSL, `-Wl,-rpath`). On macOS, build and test inside the Docker images (see the Building page of the wiki) rather than natively.

Dependencies: pthreads, OpenSSL (`-lssl -lcrypto`), libm, optionally zlib (`-lz`, with `ZLIB=1`, for the gzip of the HTTP responses), and libcurl (only for the web integration test clients).

## Build

The `makefile` is controlled by variables:
- `TYPE=development` (default; enables all `*_DEBUG`/`*_STATS` defines and `-g`), `test`, `beta`, `production`
- `COVERAGE=1` (only with `TYPE=test`), `NATIVE=1` (`-march=native`), `CC=g++` (the code must also compile as C++11, without `-fpermissive`), `CC=clang`
- `WERROR=1` makes every warning an error (the CI sets it): the library, the tests, the examples, the fuzzers and the benchmarks build with zero warnings in gcc, g++ and clang, in `test` and `development`; `CERVER_ZERO_INITIALIZER` (`config.h`) is the zero initializer of a struct for C and C++, and `CERVER_PRINTF_FORMAT` marks the functions with a format
- `ZLIB=1` defines `CERVER_ZLIB` and links zlib; without it the compression settings are accepted and nothing is compressed (`http_compression_available ()`). `Dockerfile.test`, `Dockerfile.fuzz` and `test.yml` build with it, `build.yml` without it, so both paths compile

```sh
make                    # build bin/libcerver.so
make examples           # build examples/bin/* against bin/libcerver.so
make test               # build all tests: objs, test app lib, units, integration, testhandler
make clean
make install            # copy libcerver.so to /usr/local/lib and headers to /usr/local/include
```

`compile.sh` builds library, examples and tests with both gcc and g++ in production mode. Keep code compiling with zero warnings under gcc, g++ and clang, with the warning flags in `COMMON` (`-Wpedantic -pedantic-errors` for C), and every `.c` / `.h` that is touched ends with a newline. The Dockerfiles use `gcc:16.2` and `debian:trixie-slim` (`Dockerfile.fuzz` and the `clang` job of `build.yml` use `debian:trixie`).

Run an example: `LD_LIBRARY_PATH=bin/ ./examples/bin/start server` (and `start client` in another terminal), or `LD_LIBRARY_PATH=bin/ ./examples/bin/web/web`. A failed `cerver_start ()` is released with `cerver_teardown ()`, never with `cerver_delete ()`.

## Tests

There is no test framework; `test/test.h` provides `test_check_*` macros that print the location and `exit(1)` on failure. Each unit test binary has a `main` that calls static `test_*` functions.

```sh
make TYPE=test -j4 && make TYPE=test -j4 test
bash test/run.sh                 # run all unit test binaries
./test/bin/http                  # run a single unit test binary (e.g. http, json, jwt, collections, utils, threads)
```

Run test binaries from the repo root — they reference relative paths such as `./test/http/keys/key.key` and `version.txt`.

How tests are linked (see the `units`, `integration-*` and `testhandler` targets in `makefile`):
- Most unit binaries link all objects from a subdirectory, e.g. `test/http/*.o` → `test/bin/http`. Adding a new `.c` file to such a directory automatically includes it; register its test functions from that directory's main file (e.g. `test/http/http.c`). New top-level test binaries need a line in `units` and in `test/run.sh`.
- `test/app/` is built into `test/bin/app/libapp.so`, a shared test application (handlers, routes, users, auth) linked by the HTTP unit tests and the integration servers.
- Integration tests are server/client pairs: servers in `test/cerver/` (TCP, port 7000) and `test/web/` (HTTP, port 8080), clients in `test/client/` and `test/client/web/` (libcurl). `bash test/integration.sh [pair ...]` builds `Dockerfile.test` (`SANITIZER=address,undefined` or `thread` builds a sanitized image) and runs each pair with `test/pair.sh` inside one container: the server and the client run together, with a readiness probe, deadlines, gdb stacks on a hang and both exit codes checked. `test.sh` and `.github/workflows/test.yml` use it.
- The clients wait by condition with `test_wait_counter ()` (`test/test.h`), never with fixed sleeps; counters written by other threads use `test_counter_add ()`.
- `test/cerver/core.c` (`test/bin/cerver/core`) is a TCP cerver in the same process: dispatch with POLL and THREADS, multiple handlers, auth, inactive clients, update threads, teardown with connected clients and the cerver events. `test/client/lifecycle.c` covers the client connections against a fake cerver (async connects, reconnection, many clients).
- `bash test/repeat.sh <test/bin/... | pair> [count]` is the flaky hunter: it repeats a binary or a pair in the test image, saves gdb stacks if something hangs and leaves the logs of the run that failed in `repeat-artifacts/` (`ARTIFACTS`). `test_run ()` (`test/test.h`) prints the name of each test before it runs it. `RUNNER="valgrind ..." bash test/run.sh` runs the unit tests under valgrind.
- `test/routing.c` is a balancer in the same process with two real services (round robin, handler id, reconnection, a 1 MB packet, no services), `test/client/features.c` covers the 1.x client features (states, async connect, send queue, reconnection), `test/socket.c` and `test/network.c` the sends with deadline and the addresses, and the `balancer/*` and `cerver/queue` pairs run in `integration.sh`. The process pairs `balancer/{reconnect,large,unavailable,concurrent,abandon}` put the balancer (`test/cerver/load.c`) in front of two `test/cerver/upstream.c` services, restarted by `test/supervise.sh` when the client asks one to stop, with the clients of `test/client/load/` (`balancer.c` has their common code). `bash test/allocations.sh` counts the core allocations per connection (POLL, THREADS) and per packet of a handler with its own queue. A build with `SANITIZER` (and the fuzzers) defines `CERVER_RECYCLE_DISABLED`, so the free-lists do not hide a use after free.
- Fuzzing: `test/fuzz/*.c` are libFuzzer targets (`request`, `multipart`, `url`, `json`, `jwt`, `tree`, and the core ones `receive`, `packet`, `client`, `file`, `datagram`, `address`, `serializer`, `game`) built with `make TYPE=test CC=clang fuzz` in `Dockerfile.fuzz`; `SECONDS_PER_TARGET=30 bash test/fuzz.sh [target ...]` runs them from the seeds in `test/fuzz/corpus/` and leaves crashes in `fuzz-artifacts/`.
- `bash test/performance.sh` (needs valgrind) fails on allocations per request above the current ones, load errors or 503s, req/s below half of `benchmarks/baseline.txt` for the architecture, or a routes tree less than 2x faster than the 2.0b-58 matcher on the synthetic tables of `benchmarks/routes/` (made by `benchmarks/generate.py`). `bash test/nginx/run.sh` runs the `test/web/features.c` server behind nginx (`NGINX_IMAGES`, by default the version of production, 1.31.6, and the stable one, 1.30.6), with an upstream `keepalive`, the forwarded headers and a location without buffering: the `test/client/web/features.c` client with `FEATURES_PROXY=1` (the same client of the standalone `web/features` pair) and then the load, failing on any 502 or upstream reset.
- `test/http/features.c` is a web cerver in the same process for the headers that cerver adds (Date, X-Request-Id, CORS, Vary), ETag / 304, gzip, streams, chunked bodies with trailers, the client's address and the metrics; `test/http/{date,conditional,compression,proxy}.c` are their units.
- `test/http/disconnect.c` (2.0b-65) is a web cerver in the same process whose raw clients leave in every part of the process in four ways (a close, a reset, a half-close and vanishing): the requests cut at each byte (the expected stage comes from the rules of the parser), the handler that asks for its client's state (also from the thread of a worker), the large responses cut after some bytes (gzip included), the statuses that are not 200 (304, 404, 405, 500, 401, 413), a `recv` interrupted by a signal, the queue, the pipeline, the 503 and the drain. After each batch the counters must change exactly (`n_aborted_requests[stage][reason]`, `n_vanished_requests[stage]`, `n_failed_responses`), the fds must be the ones it had and the uploads path must be empty. `test/run.sh` runs a sample (`DISCONNECT_LEVEL=sample`, the seed is printed, `DISCONNECT_SEED` repeats it); `bash test/disconnect.sh` runs every offset with `DISCONNECT_ONLY=1` in the normal, ASan+UBSan and TSan images (valgrind with the sample) in both families. Behind nginx, `test/web/disconnect.c` and `test/client/web/disconnect.c` run in the three configurations of `test/nginx/` (`CONFIGS`: `direct` with HTTP/1.1 and an unbuffered location, `services` with HTTP/1.0 and buffering, `pair` with two instances, one of them crashing on `/crash`).
- `.github/workflows/scheduled.yml` (`workflow_dispatch`, dispatched by the cron of `master`) runs the TSan pairs, the flaky hunter, long fuzzing, performance, nginx and the disconnect matrix. The jobs run in `container: gcc:16.2`, the test ones with `--sysctl net.ipv6.conf.all.disable_ipv6=0` for the IPv6 tests.
- The routes tree is covered by `test/http/tree.c` (match table, registration errors, inheritance, middlewares, compatibility, group roots, admin routes in groups, the routes json, fuzz) and end to end by `test/http/receive.c` and the `test/web/router.c` pair. `make tree` builds `benchmarks/bin/tree`.
- `test/bin/version` checks that `CERVER_VERSION` in `include/cerver/version.h` matches `version.txt` (run by CI on `master`/`*beta`).

Coverage: `bash coverage.sh` (builds with `TYPE=test`, runs units, then `make coverage`).

## Architecture

Headers live in `include/cerver/` and mirror `src/cerver/` one-to-one (`src/cerver/http/route.c` ↔ `include/cerver/http/route.h`). Public functions are marked `CERVER_EXPORT` (`config.h`) and declarations are wrapped in `extern "C"`. Enums and their string conversions are generated with X-macro `*_MAP(XX)` tables — extend the map rather than the enum directly.

Core flow:
- `cerver.c` — `Cerver` lifecycle (create, configure, start, teardown) and its handler type: `CERVER_HANDLER_TYPE_POLL` (single thread with `poll()`) or `THREADS` (thread per connection). A thread pool is also used for handlers.
- `client.c` / `connection.c` — a `Client` owns one or more `Connection`s; the same structures are used server-side for connected clients and in the client API for connecting to a cerver.
- `receive.c` → `packets.c` → `handler.c` — bytes are received per socket, assembled into `Packet`s (typed by `PacketType`), and dispatched to cerver-level handlers (`app_packet_handler`, `app_error_packet_handler`, `custom_packet_handler`). `Handler`s can run in dedicated threads with their own job queue.
- `auth.c`, `sessions.c`, `admin.c` — optional authentication, session ids, and an admin cerver for managing clients.
- `game/` — lobbies, players, game types for the game server template.
- `threads/` — `thpool` (bounded ring buffer queue, joinable threads, `thpool_drain`, overload `wait`/`reject`), `jobs` (job queues), `worker`, `bsem`, thread helpers (every thread created by cerver blocks SIGINT/SIGTERM).
- `collections/` — `dlist`, `avl`, `htab`, `pool`, `queue`, `arena` used throughout instead of external containers.
- Lifecycle: `cerver_stop_request` (EINTR in accept/poll = stop; a request before `cerver_start` cancels it, `stop_requested`, so a cerver is started once), `cerver_teardown` drains the thpool before releasing anything; the state shared by the HTTP cervers of a process (jwt pool, responses producer, common responses, multi-parts pool) is created by the first one that starts and released by the last one that ends (`http_cervers` in `http.c`), the producer follows a cerver that is still alive; web worker threads keep a `HandlerThreadContext` (arena + buffers) and the request data lives only during its handler.
- `receive.c` — `receive_handle_buffer` assembles TCP packets split between `recv ()` calls, shared by the cerver and the client.
- `types/string.c`, `utils/` (log, base64, sha256, misc) — shared helpers.

HTTP layer (`http/`), used when the cerver type is `CERVER_TYPE_WEB`:
- `http.c` — `HttpCerver` attached to a cerver: routes tree, static paths, uploads config, JWT keys/alg, origins whitelist, default response headers, custom data, stats; the parser callbacks select the endpoint in `on_headers_complete` (match, method, auth) and dispatch it in `on_message_complete` (endpoint, automatic OPTIONS, opt-in 405, 308 redirect or catch all).
- `tree.c` — the routes API: `HttpGroup` (prefix and settings inherited by its subgroups and endpoints), `HttpEndpoint` (a handler for a `(path, method)` with its own auth, custom data, modifier, max body, CORS, etag, compression and middlewares) and the radix tree of segments built in `cerver_start` (`http_tree_compile`). The match never allocates and the priority is always static > param (validated ones first) > wildcard, with backtracking, whatever the registration order. Registration errors stop the cerver. `http_group_root_add (group, method, handler)` adds the endpoint of the group's own path (pycerver: `HttpGroup.create / subgroup (prefix, method, handler, **settings)`), and `http_cerver_routes_generate_json` dumps the compiled endpoints (method, path, auth, modifier, compatibility, cors, etag, compression) for tests. A cerver without routes of the first API gets the admin routes as endpoints of its first top level group (`http_cerver_admin_group_init`), added only once (`admin_routes_ready`) by `cerver_start` or `http_cerver_routes_compile`.
- `compatibility.c` — translates the first routes API (`HttpRoute` from `route.c`: `http_route_create`, `http_route_child_add`, `http_cerver_route_register`) into endpoints when the cerver starts; a conflict there is only a warning. Deprecated, removed in 3.0.
- `middleware.c` / `validator.c` — `before` / `after` middleware chains (cerver → groups → endpoint) and the route param validators (`:id<objectid>`, `int`, `uuid`, custom).
- `request.c` / `response.c` / `headers.c` / `multipart.c` / `url.c` / `origin.c` / `admin.c` / `auth.c` — request parsing (params are slices of the url, decoded on demand; custom headers live in the request arena; header names are found with a hash table; the request id and the client's address are resolved in `on_headers_complete`), responses, multipart uploads, CORS origins, HTTP admin routes (with `cerver/metrics`), JWT auth.
- Every response goes through `http_response_send_message ()` (`response.c`): one `sendmsg` of four parts, the compiled header without its empty line, the headers that cerver adds for the request (`Date`, `X-Request-Id`, `Access-Control-Allow-Origin` + `Vary` of an endpoint with `cors`, `ETag`, `Content-Encoding`), the empty line and the body, without the body for a HEAD. A header that the response already has is not added, and nothing is allocated (`test/performance.sh` counts it). With the endpoint's `etag` a GET is answered with 304 when its If-None-Match matches, and with `compression` the body is gzipped into the request arena and the header copied without its Content-Length.
- `date.c` (the IMF-fixdate cached per thread and second), `conditional.c` (entity tags, If-None-Match / If-Modified-Since), `compression.c` (Accept-Encoding, compressible types, gzip with zlib's memory in the arena), `stream.c` (`http_response_stream_begin / write / end`: chunked to HTTP/1.1, close delimited to 1.0, ended by cerver after the handler), `proxy.c` (`HTTP_TRUSTED_PROXIES_MAP`: none by default, a CIDR list, the private networks or all; X-Forwarded-For from right to left, then X-Real-IP), `metrics.c` (the Prometheus text of the cerver and of every endpoint, with the latency histogram of `HttpRouteStats`).
- cerver always closes the connection after a response and every response says `Connection: close` (the 502 behind nginx); keep-alive waits for the event loop of the 2.1 line (`nightly`).
- `HttpReceive.responded` is set by `http_response_send_vector ()` whenever cerver tries to send, even if it fails: before the request is completed the rest of it is not handled, and after the dispatch a request without a response is answered with `server_error` (500) and counted in `n_unanswered_requests` (`cerver_http_requests_unanswered_total`).
- The responses are sent with `socket_send_vector_until ()` and `socket_send_file_until ()` of the core (`socket.c`), with one deadline for all the sends of a response (`HttpReceive.send_deadline`, set by its first send, `http_cerver_set_send_timeout_milliseconds ()` or the cerver's `send_timeout` in secs): `sendmsg` with `MSG_DONTWAIT` waits with `poll (POLLOUT)` until the deadline, and `sendfile` runs with the `SO_SNDTIMEO` limited to what is left of it, so the `SO_SNDTIMEO` of a blocking socket never extends it; each piece of a stream has its own deadline. Files and videos share `http_response_send_file_pipe ()`.
- The files of a static path with authentication (`http_static_path_set_auth ()`, `_set_decode_data ()`, `_set_authentication_handler ()`) are authenticated in `on_headers_complete` with the static path that has the file, or with the first protected one when none has it (a missing file answers like a protected one).
- A cerver of the protocol of cerver creates its thpool only with `CERVER_HANDLER_TYPE_THREADS`; a web cerver handles each request in its thpool with POLL or THREADS (`cerver_uses_thpool ()`).
- Connections, sockets, receives and clients are recycled in bounded free-lists (`collections/freelist.c`), with their stats and synchronization values inside them: a GET is 2 allocations and a POST JSON 20 (`test/performance.sh`).
- The teardowns join the handlers threads (`handler_stop ()`), wait for the event and error actions that run in their own threads and for the detachable connection threads (`ThreadGroup`, `threads/thread.c`); a drain that times out waits `CERVER_DRAIN_GRACE_TIMEOUT` more seconds and logs what is still alive.
- The default uploads generators add a sequence that the request takes from its `HttpCerver` the first time a generator asks for it: files `fd-time-sequence-index-name`, directories `fd-time-sequence`.
- Vendored third-party code: `http_parser.c` (Joyent/Node http-parser), `http/json/` (Jansson-derived JSON), `http/jwt/` (libjwt-derived JWT over OpenSSL); `thirdparty.md` lists them with their licenses. Since the 2.0b-69 the JWT (`jwt.c`), `json/value.c` and the table of `json/hashtable.c` follow the whole cerver style, and no `goto` is left in the JSON; the names of the rest of `json.c` are the 2.0b-71 (`roadmap.md` §4.3.13). The lookup3 hash of `hashtable.c` and the license headers stay as upstream.
- JWT (2.0b-67): `jwt/key.{h,c}` is cerver's own: a `JwtKey` is created once per algorithm (the HS secret or the `EVP_PKEY` of RS / ES, with its type and curve checked; `jwt_key_check_strength ()`) and signs / verifies (HMAC in constant time, ES with a low S). The `HttpCerver` loads its keys as `JwtKey` in `http_cerver_init` (a key that does not fit the algorithm stops the cerver, `JWT_ALG_NONE` is rejected by the setter) and every bearer goes through `http_cerver_auth_jwt_verify ()` (`auth.c`): `jwt_decode_with_key ()` (the header must name the algorithm of the key), the max size, `exp` / `nbf` with the leeway, `iss`, `aud`. Tokens are parsed strictly (canonical base64url of `utils/base64.c`, objects without repeated keys). The old `jwt_decode ()` with a raw key stays for the upstream tests in `test/jwt/`; `test/http/tokens.c` covers the cerver path.
- JSON (2.0b-67): the hash seed comes from `getentropy ()` (set in `http_cerver_global_init`), a parse can allocate `JSON_PARSER_DEFAULT_MEMORY_FACTOR` bytes per byte it reads (`json_set_parser_memory_factor ()`), the numbers use a "C" `locale_t`, `http_response_json_*` build their bodies with the library (escaped, owned by the response). The internal methods (`hashtable_*`, `utf8_*`, `jsonp_*`) are `CERVER_HIDDEN` (not exported); the `json_*` names stay the ones of Jansson (libauth uses them). `test/json/safety.c` covers it; `json_tests_seed ()` runs first so the seed race is seen by TSan. `cerver/config.h` includes `<stdarg.h>`: its old `va_copy` with `memcpy ()` broke the json pack / unpack of clang in x86-64.
- Hot objects (2.0b-68): `http/recycle.{h,c}` keeps a cache per thread (and shared `FreeList`s) of `HttpResponse` and of buffers in power of 2 classes (2^8 to 2^16), the pattern of `packets.c`; nothing is recycled with `CERVER_RECYCLE_DISABLED` (the sanitizer builds). `http_response_delete ()` recycles the response, its header is written in its `header_buffer` when it fits (never `free ()` `response->header` directly), and its 64 headers are only cleared when `n_headers` says they were used. The body `String` of a request lives in its arena with a recycled buffer (`max_len` is the class size), and the file stats of a request too. `performance.sh` expects GET 0 and POST JSON 14 allocations (the 14 are the handler's `json_loads ()`).

## Conventions

- Code style: tabs, a space before call parentheses (`foo (bar)`) in every file, vendored code included, `#pragma region` blocks to group sections. Exceptions: a function-like macro name in its `#define NAME(x)` can not have a space, and the X-macro tables keep their existing form (`XX(...)` entries, `*_MAP(XX)` inside functions); X-macro arguments are stringified with `#`, so their text must not be changed.
- No literal values inside functions: sizes, lengths, prefixes, separators and timeouts are named constants (`#define` in the header or a `static const` at the top of the source file), e.g. `HTTP_ERROR_BUFFER_SIZE` instead of `char error_buffer[64]`. Applied to new code now; the rest of the codebase is migrated later.
- Keep `if` / `case` bodies short: when a branch needs its own variables or more than a couple of statements, move it to a dedicated `static` function and call it from the branch. Applied to new code now; the rest of the codebase is migrated later.
- Source files have a one-word name (`tree.c`, `compatibility.c`), never `route_compat.c`; `http_parser.c` is vendored.
- `CHANGELOG.md` holds only the current version's changes, grouped under headings (`## HTTP`, `## Tests`, …), one line per commit message.
- Version bumps are a dedicated commit ("Updated version to Beta 2.0b-N") that updates `version.txt`, `include/cerver/version.h` (version, name, date, time), `ARG CERVER_VERSION` in `Dockerfile`, `cerver-install.sh`, and replaces `CHANGELOG.md` with that version's commit messages. `version.txt` and `CERVER_VERSION` must match or the version CI check fails.
- `docs/` is a git submodule (`ermiry/cerver-docs`).
