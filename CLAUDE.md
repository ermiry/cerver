# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Cerver is a C11 framework for building servers, built as a shared library (`bin/libcerver.so`). It supports five server types (`CERVER_TYPE_CUSTOM`, `GAME`, `WEB`, `FILES`, `BALANCER`), and a client API for connecting to cervers. The core (everything outside `http/`) is the one of the 1.8 line (branch `core`), ported in 2.0b-63, 2.0b-64 and 2.0b-66 (the whole 1.8: UDP, IPv6, the pools and workers, the portable 32 bytes header with the balancer's route id, the serializer by schema, the histograms and request handlers, game, zero warnings) and in 2.0b-70 (the 1.8.1: the fixes found while documenting the core, `examples/start.c`): `src/` and `include/` outside `http/` are identical to the ones of `core` except the web parts of `cerver.{h,c}` and `handler.{h,c}` (a web cerver never sends the cerver teardown packet into its HTTP connections), and fixes and features of the core land in `core` first and are seeded here. What `http` changed first in files of the core (`config.h`, `utils/base64.{h,c}`) goes back to `core` in the 1.8.2. The integration pairs run in IPv4 and in `::1` (`CERVER_TEST_ADDRESS`, `test/address.h`), new source files of the repo end with a newline. It targets Linux with gcc (uses `_GNU_SOURCE`, pthreads, OpenSSL, `-Wl,-rpath`). On macOS, build and test inside the Docker images (see the Building page of the wiki) rather than natively.

Dependencies: pthreads, OpenSSL (`-lssl -lcrypto`), libm, optionally zlib (`-lz`, with `ZLIB=1`, for the gzip of the HTTP responses), and libcurl (only for the web integration test clients).

## Build

The `makefile` is controlled by variables:
- `TYPE=development` (default; enables all `*_DEBUG`/`*_STATS` defines and `-g`), `test`, `beta`, `production`
- `COVERAGE=1` (only with `TYPE=test`), `NATIVE=1` (`-march=native`), `CC=g++` (the code must also compile as C++11, without `-fpermissive`), `CC=clang`
- `WERROR=1` makes every warning an error (the CI sets it): the library, the tests, the examples, the fuzzers and the benchmarks build with zero warnings in gcc, g++ and clang, in `test` and `development`; `CERVER_ZERO_INITIALIZER` (`config.h`) is the zero initializer of a struct for C and C++, and `CERVER_PRINTF_FORMAT` marks the functions with a format
- `ZLIB=1` defines `CERVER_ZLIB` and links zlib; without it the compression settings are accepted and nothing is compressed (`http_compression_available ()`). `Dockerfile.test`, `Dockerfile.fuzz` and `test.yml` build with it; in `build.yml` gcc builds without it and g++, clang, valgrind and the sanitizers with it, so both paths compile and the units of permessage-deflate run under each of them

```sh
make                    # build bin/libcerver.so
make examples           # build examples/bin/* against bin/libcerver.so
make test               # build all tests: objs, test app lib, units, integration, testhandler
make clean
make install            # copy libcerver.so to /usr/local/lib and headers to /usr/local/include
```

`compile.sh` cleans and builds the library with the development flags. Keep code compiling with zero warnings under gcc, g++ and clang, with the warning flags in `COMMON` (`-Wpedantic -pedantic-errors` for C), and every `.c` / `.h` that is touched ends with a newline. The Dockerfiles use `gcc:16.2` and `debian:trixie-slim` (`Dockerfile.fuzz` and the `clang` job of `build.yml` use `debian:trixie`), and the workflow jobs that compile on the runner use `container: gcc:16.2` (the sanitizers run in a `docker run` of that image, because TSan needs the host's `sysctl`).

The HTTP parser is llhttp 9.4.3 (since the 2.1b-8, phase F2 of `roadmap.md`), split in `include/cerver/http/parser/{llhttp,helpers,api}.h` and `src/cerver/http/parser/{llhttp,api,http}.c`. `llhttp.c` is generated by llparse and was restyled with a verified script (the same `objdump -d` before and after): an update of llhttp is seeded again with that script, never edited by hand; `api.c`, `http.c` and the headers are edited by hand. The parser is internal since the 2.1b-12: its API is `CERVER_HIDDEN` and the objects of `http/parser/` are compiled with `-fvisibility=hidden` (`PARSEROBJS` in the `makefile`), so `libcerver.so` exports no `llhttp` symbol; code outside the library reads the fields of `HttpReceive.parser`, and `benchmarks/http-parser.c` links the objects of the parser. `thirdparty.md` lists the vendored code and its licenses.

The static analyzers (2.1b-18, the ones of the 1.9b-2 of `core`): `bash test/analyze.sh` runs gcc `-fanalyzer` (`make ANALYZER=1`), scan-build, clang-tidy (its checks are in `.clang-tidy`) and cppcheck, writes each finding as `<tool> <file> <check>` (without its line) and fails on one that is not in `test/suppressions.txt`; `Dockerfile.analyze` has the tools (`docker build -f Dockerfile.analyze -t cerver-analyze .` and `docker run --rm -v $PWD:/cerver cerver-analyze`), and the `analyzers` job of `build.yml` runs it. A finding is fixed with its test; only a false positive goes to the suppressions, and a suppression of a file hides a new finding of the same check in that file. The `-D CERVER_CRYPTO_OPENSSL` of `CRYPTO=openssl` is added with `override`, so a `DEFINES` from the command line (`make DEFINES="-D _GNU_SOURCE"`) keeps it.

Run an example: `LD_LIBRARY_PATH=bin/ ./examples/bin/start server` (and `start client` in another terminal), or `LD_LIBRARY_PATH=bin/ ./examples/bin/web/web`. A failed `cerver_start ()` is released with `cerver_teardown ()`, never with `cerver_delete ()`.

## Tests

There is no test framework; `test/test.h` provides `test_check_*` macros that print the location and `exit(1)` on failure. Each unit test binary has a `main` that calls static `test_*` functions.

```sh
make TYPE=test -j4 && make TYPE=test -j4 test
bash test/run.sh                 # run all unit test binaries
./test/bin/http                  # run a single unit test binary (e.g. http, json, jwt, collections, utils, threads)
```

Run test binaries from the repo root — they reference relative paths such as `./test/http/keys/key.key` and `version.txt`.

How tests are linked (see the `units`, `integration-*` and `testhandler` targets in `makefile`):
- Most unit binaries link all objects from a subdirectory, e.g. `test/http/*.o` → `test/bin/http`. Adding a new `.c` file to such a directory automatically includes it; register its test functions from that directory's main file (e.g. `test/http/http.c`). New top-level test binaries need a line in `units` and in `test/run.sh`.
- `test/app/` is built into `test/bin/app/libapp.so`, a shared test application (handlers, routes, users, auth) linked by the HTTP unit tests and the integration servers.
- Integration tests are server/client pairs: servers in `test/cerver/` (TCP, port 7000) and `test/web/` (HTTP, port 8080), clients in `test/client/` and `test/client/web/` (libcurl). `bash test/integration.sh [pair ...]` builds `Dockerfile.test` (`SANITIZER=address,undefined` or `thread` builds a sanitized image) and runs each pair with `test/pair.sh` inside one container: the server and the client run together, with a readiness probe, deadlines, gdb stacks on a hang and both exit codes checked. `test.sh` and `.github/workflows/test.yml` use it.
- The clients wait by condition with `test_wait_counter ()` (`test/test.h`), never with fixed sleeps; counters written by other threads use `test_counter_add ()`.
- `test/cerver/core.c` (`test/bin/cerver/core`) is a TCP cerver in the same process: dispatch with POLL and THREADS, multiple handlers, auth, inactive clients, update threads, teardown with connected clients and the cerver events. `test/client/lifecycle.c` covers the client connections against a fake cerver (async connects, reconnection, many clients).
- `bash test/repeat.sh <test/bin/... | pair> [count]` is the flaky hunter: it repeats a binary or a pair in the test image, saves gdb stacks if something hangs and leaves the logs of the run that failed in `repeat-artifacts/` (`ARTIFACTS`). `test_run ()` (`test/test.h`) prints the name of each test before it runs it. `RUNNER="valgrind ..." bash test/run.sh` runs the unit tests under valgrind.
- `test/routing.c` is a balancer in the same process with two real services (round robin, handler id, reconnection, a 1 MB packet, no services), `test/client/features.c` covers the 1.x client features (states, async connect, send queue, reconnection), `test/socket.c` and `test/network.c` the sends with deadline and the addresses, and the `balancer/*` and `cerver/queue` pairs run in `integration.sh`. The process pairs `balancer/{reconnect,large,unavailable,concurrent,abandon}` put the balancer (`test/cerver/load.c`) in front of two `test/cerver/upstream.c` services, restarted by `test/supervise.sh` when the client asks one to stop, with the clients of `test/client/load/` (`balancer.c` has their common code). `bash test/allocations.sh` counts the core allocations per connection (POLL, THREADS) and per packet of a handler with its own queue. A build with `SANITIZER` (and the fuzzers) defines `CERVER_RECYCLE_DISABLED`, so the free-lists do not hide a use after free.
- Fuzzing: `test/fuzz/*.c` are libFuzzer targets (`request`, `lenient` (the requests with the lenient flags of the parser), `pipeline` (the requests of a connection that is kept, with `http_receive_reset ()` between them and the receive prepared with an arena), `multipart`, `url`, `json`, `jwt`, `tree`, `frame` and `handshake` (WebSocket), and the core ones `receive`, `packet`, `client`, `file`, `datagram`, `address`, `serializer`, `game`) built with `make TYPE=test CC=clang fuzz` in `Dockerfile.fuzz`; `SECONDS_PER_TARGET=30 bash test/fuzz.sh [target ...]` runs them from the seeds in `test/fuzz/corpus/` and leaves crashes in `fuzz-artifacts/`; they are built with `-fno-sanitize-recover=undefined`, so the first undefined behavior that UBSan finds fails its target. The second byte of the input of `frame` is the compression that was negotiated (the peer that resets its context, the window bits). The long fuzzing of `scheduled.yml` is a job for each target.
- `bash test/performance.sh` (needs valgrind) fails on allocations per request above the current ones (the ones of 1024 requests after 256 of warm-up, counted without rounding: GET 0, POST JSON 14), a server that ends with an error or that has to be killed, load errors or 503s, req/s below half of `benchmarks/baseline.txt` for the architecture, or a routes tree less than 2x faster than the 2.0b-58 matcher on the synthetic tables of `benchmarks/routes/` (made by `benchmarks/generate.py`). `bash test/nginx/run.sh` runs the `test/web/features.c` server behind nginx (`NGINX_IMAGES`, by default the version of production, 1.31.6, and the stable one, 1.30.6), with an upstream `keepalive`, the forwarded headers and a location without buffering: the `test/client/web/features.c` client with `FEATURES_PROXY=1` (the same client of the standalone `web/features` pair) and then the load, failing on any 502 or upstream reset.
- `test/faults/` defines `malloc ()`, `calloc ()`, `realloc ()` and `pthread_create ()` to make one call fail (`faults_arm ()` by its function and its size): a check of an allocation gets its test there (`core.c` the core, `http.c` HTTP, `websockets.c` WebSocket, since the 2.1b-18 the first two). It is built only without a sanitizer and `test/run.sh` runs it only without `RUNNER`. gcc can merge a `malloc ()` and its `memset ()` into a `calloc ()`, so a test arms both; the size of the call that fails must not be the one of another allocation of the same path.
- `test/http/features.c` is a web cerver in the same process for the headers that cerver adds (Date, X-Request-Id, CORS, Vary), ETag / 304, gzip, streams, chunked bodies with trailers, the client's address and the metrics; `test/http/{date,conditional,compression,proxy}.c` are their units.
- `test/http/disconnect.c` (2.0b-65) is a web cerver in the same process whose raw clients leave in every part of the process in four ways (a close, a reset, a half-close and vanishing): the requests cut at each byte (the expected stage comes from the rules of the parser), the handler that asks for its client's state (also from the thread of a worker), the large responses cut after some bytes (gzip included), the statuses that are not 200 (304, 404, 405, 500, 401, 413), a `recv` interrupted by a signal, the queue, the pipeline, the 503 and the drain. After each batch the counters must change exactly (`n_aborted_requests[stage][reason]`, `n_vanished_requests[stage]`, `n_failed_responses`), the fds must be the ones it had and the uploads path must be empty. `test/run.sh` runs a sample (`DISCONNECT_LEVEL=sample`, the seed is printed, `DISCONNECT_SEED` repeats it); `bash test/disconnect.sh` runs every offset with `DISCONNECT_ONLY=1` in the normal, ASan+UBSan and TSan images (valgrind with the sample) in both families. Behind nginx, `test/web/disconnect.c` and `test/client/web/disconnect.c` run in the three configurations of `test/nginx/` (`CONFIGS`: `direct` with HTTP/1.1 and an unbuffered location, `services` with HTTP/1.0 and buffering, `pair` with two instances, one of them crashing on `/crash`).
- `test/bin/websockets` (`test/websockets/`) has the units of the text, the frames (split at every byte), the messages (the close codes), the handshake and permessage-deflate (the examples of RFC 7692 sections 7.2.3.1, 7.2.3.2 and 7.2.3.4, a message that is cut, a decompression bomb), and two suites in the same process: `server.c` (a web cerver with raw clients of `raw.c`: the rejections of an upgrade one by one with the places that they give back, what `on_upgrade` decides and the headers that it adds to the 101, echoes of every size, frames with the request, fragments, both closes, each protocol error with its code, abrupt clients, ping / pong and `on_ping` / `on_pong`, 8 threads sending to one connection, the owner of a connection in each model and the queue that is written while a method blocks, the drop and close policies of the queue with `on_drain`, rooms without limits and the targets, broadcast, a slow reader, the limit, the teardown with clients that answer its 1001 and with clients that do not, the settings that a group gives to its subgroups and endpoints, streaming, compression, metrics and stats, and the fds after each server) and `client.c` (the public client against a cerver and against fake servers that answer wrong on purpose, the reconnection and the ways it ends, the messages of 8 threads checked one by one). The short timeouts of both use `test_milliseconds ()` (`test/test.h`): `TEST_TIME_SCALE` multiplies them, 4 in a build with a sanitizer and under the `RUNNER` of `test/run.sh`. The `frame` and `handshake` fuzzers cover the receiver and the handshakes. `bash test/autobahn/run.sh` runs autobahn-testsuite (`crossbario/autobahn-testsuite:25.10.1`, amd64) against the server (`test/web/autobahn.c`) and the client (`test/client/web/autobahn.c`) and fails on any case that is not OK, NON-STRICT or INFORMATIONAL, and on a report that does not have its 517 cases (`test/autobahn/check.py`); `web/websocket` is a pair, also behind nginx (`/websocket/`); `test/performance.sh` checks 0 allocations per WebSocket message (`benchmarks/messages.c`).
- `.github/workflows/scheduled.yml` (`workflow_dispatch`, dispatched by the cron of `master`) runs the TSan pairs, the flaky hunter, long fuzzing, performance, nginx, the disconnect matrix and autobahn with the sanitizers. The jobs run in `container: gcc:16.2`, the test ones with `--sysctl net.ipv6.conf.all.disable_ipv6=0` for the IPv6 tests.
- The routes tree is covered by `test/http/tree.c` (match table, registration errors, inheritance, middlewares, compatibility, group roots, admin routes in groups, the routes json, fuzz) and end to end by `test/http/receive.c` and the `test/web/router.c` pair. `make tree` builds `benchmarks/bin/tree`.
- The parser is covered by the `parser` region of `test/http/receive.c` (the methods of llhttp, each strict difference with http_parser rejected and accepted with its lenient flag, the protocols and the versions that are not served, what is rejected with every flag, upgrades, keep-alive and pipelining, the always active headers limit) and by the `request` and `lenient` fuzzers; `benchmarks/http-parser.c` measures llhttp alone (`make bench`) and, like `benchmarks/frames.c`, exits with 1 when what it measures did not happen (every request completed, every message as it was sent). `make bench tree load` builds in `build.yml` with the three compilers; `NATIVE=1` only adds `-march=native`.
- The two models (2.1b-15): the web servers of the tests take their handler type from `CERVER_TEST_HANDLER=threads|events` and their I/O threads from `CERVER_TEST_IO_THREADS` (`test/handler.h`); `test/http/server.c`, `test/http/disconnect.c` and `test/http/features.c` run each test in THREADS and in EVENTS inside the binary (with the tests that only apply to the loops), `test/http/receive.c` feeds every request also through an event loop with an inline dispatcher (`event_loop_adopt ()` and `event_loop_step ()` over a socket pair) and tests the parked requests with a manual dispatcher and its own clock; `test/bin/events` (`test/events/`) has the units of the poller and the wheel; `test/run.sh` runs `faults` and `websockets` once per model, `test/integration.sh` and `test/nginx/run.sh` (`HANDLERS="threads events"`) run the web pairs and nginx in both, `test/performance.sh` the allocations and the load, and `test/autobahn/run.sh` takes one (`HANDLER`); `test/performance.sh` also fails when EVENTS is below 90 % of the req/s of THREADS (medians of 5 runs), and below 90 % of the WebSocket msg/s of THREADS with a pool of one thread for each core when the connections are not more than its threads (more connections are only measured, 2.1b-21); the fuzzer `loop` feeds an event loop with an inline dispatcher.
- The connections that are kept (2.1b-16): `test/http/keepalive.c` has its own cervers and clients that read each response by its `Content-Length` (N requests, pipelining, HTTP/1.0, the limit of requests, the idle timeout, a response without its length, the state between requests, the rejections, an upgrade, the drain, the limit of connections, threads under pressure); `test/http/server.c`, `disconnect.c` and `features.c` call `http_cerver_set_keep_alive (false)` because their clients read each response until the cerver closes the connection. A test that reads what the thread of a cerver wrote when it started waits first for a counter that a handler adds with `test_counter_add ()` (a `connect ()` gives no order, TSan reports it). `CERVER_TEST_KEEP_ALIVE=0|1` (`test/handler.h`) sets it in the `test/web/features.c` and `disconnect.c` servers, and `test/client/web/features.c` expects `Connection: close` or its absence from it. `test/nginx/run.sh` has three ways of handling (`HANDLERS="threads events keep"`, `keep` is threads with keep-alive), checks with `cerver_http_reused_connections_total` that the load reached the cerver through kept connections (none with `threads`), and has the configuration `restart` (`restart.conf`, the profile `restart` of its compose): two cervers that restart one at a time under load, where every request is answered; `PROJECT` names its compose project, so two runs do not collide. `benchmarks/load` sends `Connection: close` unless `LOAD_KEEP_ALIVE` is set (then each of its threads keeps a connection and it prints how many it opened), `benchmarks/server` takes `BENCH_KEEP_ALIVE`, and `test/performance.sh` also counts the allocations with kept connections and fails when they give less than 150 % of the req/s of a connection by request (medians of 5 runs, with the event loops). The fuzzers `loop` and `pipeline` keep their connections: `loop` handles the requests that follow one that was answered.
- `test/bin/version` checks that `CERVER_VERSION` in `include/cerver/version.h` matches `version.txt` (run by CI on `master`/`*beta`).

Coverage: `bash coverage.sh` (builds with `TYPE=test`, runs units, then `make coverage`).

## Architecture

Headers live in `include/cerver/` and mirror `src/cerver/` one-to-one (`src/cerver/http/routes/route.c` ↔ `include/cerver/http/routes/route.h`). Since the session 47 (2026-11-13) `nightly` has the layout of `labs` 3.0b-2 and its documentation (3.0b-3): `include/`, `src/`, `test/`, `examples/` and `benchmarks/` were seeded from `labs` (with `crypto/`, the OpenSSL provider of the 3.0b-1), so the files of both lines are the same until `labs` replaces a module; the table of the old paths is in the `roadmap.md` of `labs` §11, and the `CLAUDE.md` of `labs` describes the layout (the folders by domain, `cerver.h` and `http/http.h` as umbrellas, the parts of the big files, the `internal.h` in `src/`, the includes at the start in blocks, `_with_` instead of `_by_`). Some paths of the sections below are still the old ones. Public functions are marked `CERVER_EXPORT` (`config.h`) and declarations are wrapped in `extern "C"`. Enums and their string conversions are generated with X-macro `*_MAP(XX)` tables — extend the map rather than the enum directly.

Core flow:
- `cerver.c` — `Cerver` lifecycle (create, configure, start, teardown) and its handler type: `CERVER_HANDLER_TYPE_POLL` (single thread with `poll()`), `THREADS` (thread per connection) or `EVENTS` (the event loops, only for a web cerver, since the 2.1b-15). A thread pool is also used for handlers.
- `client.c` / `connection.c` — a `Client` owns one or more `Connection`s; the same structures are used server-side for connected clients and in the client API for connecting to a cerver.
- `receive.c` → `packets.c` → `handler.c` — bytes are received per socket, assembled into `Packet`s (typed by `PacketType`), and dispatched to cerver-level handlers (`app_packet_handler`, `app_error_packet_handler`, `custom_packet_handler`). `Handler`s can run in dedicated threads with their own job queue.
- `auth.c`, `sessions.c`, `admin.c` — optional authentication, session ids, and an admin cerver for managing clients.
- `game/` — lobbies, players, game types for the game server template.
- `threads/` — `thpool` (bounded ring buffer queue, joinable threads, `thpool_drain`, overload `wait`/`reject`), `jobs` (job queues), `worker`, `bsem`, thread helpers (every thread created by cerver blocks SIGINT/SIGTERM).
- `collections/` — `dlist`, `avl`, `htab`, `pool`, `queue`, `arena` used throughout instead of external containers.
- Lifecycle: `cerver_stop_request` (EINTR in accept/poll = stop; a request before `cerver_start` cancels it, `stop_requested`, so a cerver is started once), `cerver_teardown` drains the thpool before releasing anything; the state shared by the HTTP cervers of a process (jwt pool, responses producer, common responses, multi-parts pool) is created by the first one that starts and released by the last one that ends (`http_cervers` in `http.c`), the producer follows a cerver that is still alive; web worker threads keep a `HandlerThreadContext` (arena + buffers) and the request data lives only during its handler.
- `receive.c` — `receive_handle_buffer` assembles TCP packets split between `recv ()` calls, shared by the cerver and the client.
- `types/string.c`, `utils/` (log, base64, sha256, misc) — shared helpers.

HTTP layer (`http/`), used when the cerver type is `CERVER_TYPE_WEB`:
- `http.c` — `HttpCerver` attached to a cerver: routes tree, static paths, uploads config, JWT keys/alg, origins whitelist, default response headers, custom data, stats; the parser callbacks select the endpoint in `on_headers_complete` (match, method, auth) and dispatch it in `on_message_complete` (endpoint, automatic OPTIONS, opt-in 405, 308 redirect or catch all). The `llhttp_t` is embedded in `HttpReceive` with its own settings; the url is closed in `on_url_complete` and each header in `on_header_value_complete`; a callback that rejects returns `HTTP_RECEIVE_PARSER_STOP`; `on_message_complete` returns `HPE_PAUSED` (one request per connection) and keeps `keep_alive_requested` and `unparsed` for the keep-alive of F4. Strict by default, `http_cerver_set_parser_lenient ()` (`HttpParserLenient`, without the header value relaxed flag of llhttp, that loops forever with a NUL). The url and headers limits are always active.
- `method.h` — the only table of methods (`REQUEST_METHOD_MAP`, the values of llhttp: 34 HTTP methods and `QUERY`, `REQUEST_METHOD_SIZE` 47, `REQUEST_METHOD_UNDEFINED` 255), all of them can be registered; the methods of RTSP are rejected by the parser (400) and `PRI` by its version (505), a method without endpoint is 405 or the catch all. Only `HTTP/1.0` and `HTTP/1.1` are served (2.1b-13): `on_protocol` / `on_protocol_complete` answer a request line of RTSP or ICE with 400, `on_version_complete` another version of HTTP with 505 (`HTTP_PARSER_LENIENT_VERSION` serves any); a `Transfer-Encoding` that does not end with `chunked` (`http_receive_body_has_no_end ()`) and a NUL in a header value are 400 also with their lenient flags.
- `tree.c` — the routes API: `HttpGroup` (prefix and settings inherited by its subgroups and endpoints), `HttpEndpoint` (a handler for a `(path, method)` with its own auth, custom data, modifier, max body, CORS, etag, compression and middlewares) and the radix tree of segments built in `cerver_start` (`http_tree_compile`). The match never allocates and the priority is always static > param (validated ones first) > wildcard, with backtracking, whatever the registration order. Registration errors stop the cerver. `http_group_root_add (group, method, handler)` adds the endpoint of the group's own path (pycerver: `HttpGroup.create / subgroup (prefix, method, handler, **settings)`), and `http_cerver_routes_generate_json` dumps the compiled endpoints (method, path, auth, modifier, compatibility, cors, etag, compression) for tests. A cerver without routes of the first API gets the admin routes as endpoints of its first top level group (`http_cerver_admin_group_init`), added only once (`admin_routes_ready`) by `cerver_start` or `http_cerver_routes_compile`.
- `compatibility.c` — translates the first routes API (`HttpRoute` from `route.c`: `http_route_create`, `http_route_child_add`, `http_cerver_route_register`) into endpoints when the cerver starts; a conflict there is only a warning. Deprecated, removed in 3.0.
- `middleware.c` / `validator.c` — `before` / `after` middleware chains (cerver → groups → endpoint) and the route param validators (`:id<objectid>`, `int`, `uuid`, custom).
- `request.c` / `response.c` / `headers.c` / `multipart.c` / `url.c` / `origin.c` / `admin.c` / `auth.c` — request parsing (params are slices of the url, decoded on demand; custom headers live in the request arena; header names are found with a hash table; the request id and the client's address are resolved in `on_headers_complete`; the query and the values of a form are split by `&` and `=` and then each key and value is decoded in its own memory, `http_query_pairs_decoded ()`; a `Range` is one that starts at a position or the one of the last bytes, `bytes=-N` with `HTTP_RANGE_TYPE_SUFFIX`, and `http_request_get_bytes_range ()` ignores the rest; since the 2.1b-13 the target of a request in absolute form is routed by its path and its fragment is dropped (`http_receive_close_url ()`), the spaces after the value of a header are removed, a repeated header is joined in memory that grows by `HTTP_HEADER_VALUES_GROWTH` with its capacity in `String.max_len`, the trailers of a chunked body and the extensions of its chunks count for the limits of the headers (`http_receive_handle_discarded ()`), the value of a custom header is limited by `http_cerver_set_max_custom_header_size ()` and the default request timeout is 300 secs), responses, multipart uploads, CORS origins, HTTP admin routes (with `cerver/metrics`), JWT auth.
- A response is structured since the 2.1b-11 (F1 of `roadmap.md`): `HttpResponse` is its status and a `HttpHeaders` (`headers.{h,c}`: the headers in the order they were added, a name can be repeated and can be any token, each one kept as its line `Name: value\r\n`, 32 fields and 512 bytes inside the list and its own memory up to 256 fields and 16 KiB; a value with CR, LF or NUL is rejected). `http_response_header_set / _add / _remove / _count / _get ()` and their `_by_name` are the API, the older `http_response_add_header ()` and friends keep replacing the header of their type. `http_response_compile_header ()` is the only serializer (status line, `Server`, the headers of the response, the ones of the cerver that it does not have, the empty line); `header` / `res` are the cache of the HTTP/1.1 form and a header or a status that changes discards them; a header set as bytes (`http_response_set_header ()`, `header_is_raw`) is sent as it is. Never write the bytes of a header by hand.
- Every response goes through `http_response_send_message ()` (`response.c`): one `sendmsg` of four parts, the compiled header without its empty line, the headers that cerver adds for the request (a `HttpHeaders` in the stack: `Connection: close` when the connection is closed after it and the response has no `Connection` of its own, `Date`, `X-Request-Id`, `Access-Control-Allow-Origin` + `Vary` of an endpoint with `cors`, `ETag`, `Content-Encoding`), the empty line and the body, without the body for a HEAD. A header that the response already has is not added (`http_response_message_find ()` looks in its headers and in the ones of the cerver, or in its bytes when only they are known), and nothing is allocated (`test/performance.sh` counts it). `HttpReceive.framed` says that the response that was sent has an end without the close of the connection (a Content-Length, a status without body, a HEAD, the last chunk of a stream, a whole file), the condition of the keep-alive of F4. With the endpoint's `etag` a GET is answered with 304 when its If-None-Match matches, and with `compression` the body is gzipped into the request arena. Both choose their headers in the lists of the response and of its cerver since the 2.1b-13 (`HttpResponseFilter`: every header but the Content-Length of the plain body, or only the ones that a 304 keeps; `http_response_message_header ()` writes them again in the arena and `http_response_message_find ()` does not find the ones that the filter dropped); the lines of a header are only read when it was set as bytes.
- `date.c` (the IMF-fixdate cached per thread and second), `conditional.c` (entity tags, If-None-Match / If-Modified-Since), `compression.c` (Accept-Encoding, compressible types, gzip with zlib's memory in the arena), `stream.c` (`http_response_stream_begin / write / end`: chunked to HTTP/1.1, close delimited to 1.0, ended by cerver after the handler), `proxy.c` (`HTTP_TRUSTED_PROXIES_MAP`: none by default, a CIDR list, the private networks or all; X-Forwarded-For from right to left, then X-Real-IP), `metrics.c` (the Prometheus text of the cerver and of every endpoint, with the latency histogram of `HttpRouteStats`).
- A connection that cerver closes after a response says `Connection: close` in it (the 502 behind nginx), added when it is sent (never compiled in a header); the 101 of an upgrade hands the connection to its WebSocket instead. What belongs to a request is separated from what belongs to its connection: a `HttpReceive` lives in the memory of its owner (`HandlerThreadContext.http_receive` in a worker thread, the `HttpConnection` of an event loop, never in the arena of its request) with the resources that it lends (`HttpReceiveResources`, `http_receive_prepare ()`); `http_receive_reset ()` ends a request (uploads, request, deleters, arena, parser with `llhttp_reset ()`) and starts the next one of the connection; the clock, the received bytes, the `recv ()` diagnostics and the headers / request deadlines are fields of the receive, and `http/access.{h,c}` (`http_access_request ()`) logs and counts a request when it ends, once per request, before its data is released. `test/http/receive.c` has the regions `framed` and `reset` (many requests through one receive, with the arena and without it).
- Keep-alive (2.1b-16, F4 of `roadmap.md` §4.4): a connection handles more than one request, by default with `CERVER_HANDLER_TYPE_EVENTS` and only when it is asked for with the other handler types (`http_cerver_set_keep_alive ()`, resolved in `http_cerver_init ()`; `http_cerver_set_keep_alive_timeout ()`, 2^7 secs, and `http_cerver_set_keep_alive_requests ()`, 2^10, in `http/core/limits.h`). The decision has two steps in `http/core/handler.c`: `http_receive_keep_alive_decide ()` when the request is complete, before it is handled, writes `HttpReceive::keep_alive` (a value of each request: the cerver keeps its connections, the client asked for it, `HttpReceive::n_requests` is under the limit, not an upgrade, `cerver_is_stopping ()` is false, and with threads no connection waits for one), so the response has its `Connection` header (`close`, nothing for HTTP/1.1, `keep-alive` for HTTP/1.0; a response with its own `close` closes the connection); `http_receive_keeps_connection ()` confirms it after the response (answered, `framed`, not failed, handled). A request that cerver rejects always closes, and its response says it: `http_receive_reject ()` sets the status of the request before it sends, and a response to a request that is not handled (`http_receive_was_handled ()`: `COMPLETED` or `UNHANDLED`) has `Connection: close` whatever `keep_alive` has (a complete request that is rejected later, like one without a body that an event loop authorizes with its handler, was already going to keep its connection; the field is not cleared, the sessions of the unit tests hold it by hand). With EVENTS the thread of the pool that answered logs the request, calls `http_receive_reset ()` and gives the connection back by itself (below); with THREADS (`handler/handler.c`) the thread stays with the connection: `cerver_receive_http_handle ()` follows each request with the next one (the bytes behind it first, a pipelined request) and `cerver_receive_http_idle ()` waits for the next request with `poll ()` in pieces, until its time ends or the cerver stops. When another connection waits for a thread the idle one is never closed (its client can be sending its next request: a 502 behind a proxy): after a short wait its thread gives it back to the queue of the thpool as it is (`cerver_receive_http_yield ()`, with `CerverReceive::n_requests` and `idle_deadline`, the last thing that the thread does with it) and takes the one that waits; a queued idle connection counts as one that waits, so a cerver with threads keeps one idle connection for each thread and says `Connection: close` to the others. A connection that ends between two requests (`http_receive_is_between_requests ()`) has no request to log. `test/http/keepalive.c` runs a real cerver in the two models, and the region `kept` of `test/http/receive.c` an event loop with the manual dispatcher and its own clock. A thread can follow its connection (2.1b-17, off by default: `http_cerver_set_keep_alive_follow ()` in microseconds, `HTTP_CERVER_KEEP_ALIVE_FOLLOW_SHORT`): the thread of the pool that answered a request of a kept connection looks for the next one in its socket for that time without sleeping (`http_connection_work_follow ()`, a `recv ()` that does not block into a buffer of the thread) and parses and handles it by itself, so that request crosses no thread; only while no job waits for a thread of its pool (`EventDispatcher::is_awaited`, `thpool_has_queued ()` without the mutex), it stops when one arrives or its loop stops, and each miss in a row doubles the requests that are not followed (`HttpConnection::follow_misses`, `follow_skip`). What the thread does not handle goes back to the loop as it is with the outcomes `READING` (not complete: the loop reads the rest), `PAUSED` (it needs another job: its authentication, another pool, a loop that rejects, a parked request that goes first) and `FAILED` (answered by the thread, the loop closes it); `http_connection_completed ()` attaches it and gives it the deadlines of a request (`http_connection_followed ()`). The tests of the region `kept` put the next request in the socket before they run the job, so nothing depends on the time; the ones with a real cerver give the thread a time longer than any client takes. Kept connections give about 150 % of the req/s of a connection by request and the minimum of `test/performance.sh` is not met in every run (`roadmap.md` §4.4 items 12 and 13): with a thread that follows its connection 4 connections on 4 threads go from 152 % to 267 %, and more connections than threads give the same or a little less (the load client shares the processors), so it is not the default.
- The whole form of keep-alive (2.1b-19, F4b of `roadmap.md` §4.4b): the threads of the pools read the next request of an idle connection, without its loop (`http_cerver_set_keep_alive_pool_read ()`, true by default; false gives back the reads of the 2.1b-18). A thpool can wait on a `ThpoolWaiter` instead of the condition of its queue (`thpool_set_waiter ()` in `threads/thpool.c`, a core file to port to the other lines; the queue always goes first, a work of the waiter is a job without a wait, and a push only asks the waiter for a wake up when more threads wait than wake ups are pending, `Thpool::waiter_wakes`, so the wake ups never pile up behind the jobs that the busy threads take: `ThpoolWaiter::wait` returns `THPOOL_WAITED_WOKEN` when it consumed one; without that count the event loops with a connection by request fell to 82 % of THREADS). `src/cerver/events/idle.c` is the `EventIdle` of each lane of the group whose pool has threads (`EventLoopGroup::idles`, `EventLane::idle`): a counted poller (`event_poller_create_counted ()`, an eventfd with `EFD_SEMAPHORE`) where an idle connection is armed once (`EVENT_LOOP_IDLE_INTEREST`) when its last request was of that pool (`event_loop_idle_poller ()`; `EventSource::poller` says where a source is, `event_poller_watch ()` moves it), and the waiter of its thpool (`event_poller_wait_one ()`, with the memory of the thread). The thread that gets a socket takes its connection out of the idle ones of its loop with the idle mutex (`http_connection_reported ()`) and reads, parses and handles it (`http_connection_work_reported ()` → `http_connection_work_read ()`, the path of the thread that follows, that also runs the authentication before the body of a request of its pool); it leaves it to its loop (`HTTP_CONNECTION_OUTCOME_REPORTED`) when the loop rejects or stops or when requests of that pool are parked in it (they go first). While no thread of a pool waits, each loop takes the ready ones in its idle check (`event_idle_rescue ()`, `event_poller_take ()` without consuming the wake ups; a connection of another loop goes to its loop), so a request waits for a place like any other. The waiters start after the threads of the loops and end at the end of `event_loop_group_finish ()`. A thread can have the pointer of a connection that its loop ended, so the struct of a connection is never freed while its loop runs (`EventLoop::stripped`, `http_connection_strip ()` / `_restore ()`), and `connection->loop` is only written when it changes. Without a group (the manual dispatcher of the tests, the fuzzer) the loop gives a reported idle connection to its dispatcher as `HTTP_CONNECTION_JOB_READ` (`http_connection_read_submit ()`), with the same read in the pool.
- The query params and the values of a form (2.1b-19) are parsed into the arena of the request (`HttpRequest::query_pairs`, `body_pairs`, `http_query_pairs_arena ()` in `http/core/pairs.c`), and `http_request_query_params_get_value ()` / `http_request_body_get_value ()` read them without allocating; `query_params` and `body_values` are only created by their getters (a copy). The pause of the accept of a loop is its own deadline (`EventLoop::accept_resume`, `EVENT_LOOP_ACCEPT_BACKOFF` 2^4 ms), and `cerver_http_pool_parked_seconds{pool}` is the histogram of the time that the requests of a pool were parked.
- `websockets/` (2.1b-9, F6a of `roadmap.md`; the folders of the packages are named in plural) is WebSocket (RFC 6455 and permessage-deflate, RFC 7692) on the threads model: `text.c` (incremental UTF-8), `frame.c` (encoder and incremental parser), `message.c` (the rules of the messages without sockets: fragments, close codes, limits, streaming), `handshake.c`, `deflate.c` (only with `ZLIB=1`; since the 2.1b-21 a window of 2^8 is accepted and compressed with 2^9, W11), `settings.c` (inherited by the groups one by one, `HttpRouteSettings.web_socket`), `websocket.c` (`HttpWebSocket`: references, its thread with `poll` on its socket and an `eventfd`, the sends with a `send_mutex` per frame and a `message_mutex` per message, the close, ping / pong), `registry.c` (`HttpCerver.web_sockets`: the limit with places reserved before the 101, rooms, broadcast, stats) and `client.c` (`HttpWebSocketClient`, with reconnection). The upgrade is checked in `on_headers_complete` (400 / 426 / 403 / 503) and answered in `on_message_complete` (before middlewares, `on_upgrade`, a raw 101); `cerver_receive_http` hands the connection to a thread of `connection_threads` (`http_web_socket_start`), and the drain sends 1001. A route of the first API with the modifier is still 501. wss:// waits for TLS (F8). Since the 2.1b-12: a stream that does not begin (`http_web_socket_send_begin ()` returns 1) holds nothing and is never ended; a frame that the connection does not take because it is closing is an error of the send that never calls `http_web_socket_fail ()` (only a write that was attempted and failed does); the deadline of a send is created after `message_mutex` is taken; the subprotocols are tokens (`http_header_name_is_valid ()`), and the methods that only cerver calls are `CERVER_HIDDEN`. Since the 2.1b-13: `HttpWebSocket`, `HttpWebSocketClient`, the registry, the handshake and the response of the client are opaque, their definitions and the hidden methods live in `src/cerver/http/websockets/internal.h` (not installed, found with `-I src`; a test that reads a field includes it), the counters are read with `http_cerver_web_socket_get_stats ()` / `http_web_socket_get_stats ()` (`HttpWebSocketStats`), the timeouts in milliseconds have the `_milliseconds` suffix, `on_upgrade` adds headers to the 101 with `http_web_socket_upgrade_add_header ()` (`HttpWebSocketUpgrade.headers`, a `HttpHeaders` in the stack of the upgrade; the 101 is sent in three parts) and the connection keeps the query of its request (`http_web_socket_get_query ()`). The methods of a connection are serialized by connection and their thread is not part of the API. A frame length that is not the shortest one is a 1002, a key that is not canonical a 400; a compressed message must end between two blocks, a block with BFINAL restarts the inflater with its window (`inflateResetKeep ()`), and `http_web_socket_deflate_decompress ()` returns `HTTP_WEB_SOCKET_INFLATE_INVALID` (1007), `_STOPPED` or `_FAILED` (1011). A message that the connection refuses because it is closing never fails it; a connection ends its writes with `SHUT_WR` and a bounded drain (`http_web_socket_end_writes ()`). In the client, `http_web_socket_client_running` (thread local) makes `wait` and `delete` safe inside its own methods, the waits of an attempt watch `wake_fd` (`http_web_socket_client_wait_socket ()`), and the backoff is `http_web_socket_client_backoff_delay ()`.
- WebSocket over the loop (2.1b-21, F6b of `roadmap.md` §4.6): with EVENTS `http_web_socket_start (cr, receive, loop)` gives the connection to its loop (`http_web_socket_loop_adopt ()`, `websockets/loop.c`), without a thread for it. The loop reads into its own buffer and parses, answers the pongs and the closing handshake, and puts the events of a read (open, messages, fragments, ping, pong, drain, end) in a batch that a job of the pool of the endpoint runs (`EventDispatcher::submit_work ()`), one at a time for each connection with `EPOLLIN` off while it runs; a job that the pool rejects waits in `EventLoop::web_sockets_waiting` (a retry every 2^4 ms), and the jobs run inline when the loop stops or the dispatcher has no jobs. Another thread asks the loop with the bits of `loop_requests` (ADOPT, OUTPUT, JOB_DONE, TIMERS, GO_AWAY, ABORT) and the list `EventLoop::web_sockets_head` (under `completed_mutex`, with a reference); `EventSourceType` has `WEB_SOCKET` and `EventTimer::owner_type` says whose timer it is. Its end is the flush of the queue, `SHUT_WR`, the drain (S5), the job of the end (on_error, on_close) and the release; a loop does not finish while its `n_web_sockets` is not 0. Between two jobs a connection waits in the poller of its pool (the pattern of F4b, `HttpWebSocketPark`: a park lives in the list of its loop and is released with it, never with its connection, and it is taken under its mutex): the thread that ended a job lingers 2^18 ns on its socket (with `ppoll`, and on the poller of the pool when no thread of the pool waits; it looks at the pool every 2^4 messages), reads and runs the next frames itself, and parks the connection when none came; a thread of the pool that gets its report reads it, and the loop takes it back (`http_web_socket_loop_unpark ()`) for its timers, its end, the go-away, the stop and its `on_drain ()` (deferred with `drain_pending` while a job has it), or reads it when no thread of the pool waits (`http_web_socket_park_rescued ()`). THREADS keeps the thread of F6a with the same API. The output queue (`websockets/queue.c`, A5) is the same in both models and in the client: one buffer per connection under `send_mutex`, a server writes a frame at once with the queue empty (`MSG_DONTWAIT`) and queues the rest, the client masks in the queue, the owner writes it (the loop with `EPOLLOUT`, the thread with `POLLOUT`); 2^20 by default, `HttpWebSocketOverflow` DROP / CLOSE (1008), BACKPRESSURE over half of it and `on_drain ()` when it is empty again; the send timeout is the time without writing a byte, and the sends return `HttpWebSocketSendResult`. `websockets/transport.c` (A24) is every read and write of a connection, but the handshake of the client. A connection is registered after `on_open ()` (S7), its ids are unique in the process (A9); the rooms are an index of the registry (A14: `Htab` name → `HttpWebSocketRoom`, each `HttpWebSocketMembership` in the list of its room and of its connection), kept during `on_close ()` and cleared after it, and `HttpWebSocketTarget` selects the connections of a count, a broadcast and a for each. After `on_close ()` zlib, the buffer of the messages and an empty queue are released (W7); a stop of the sink keeps the bytes and the output that are left (`HttpWebSocketDeflate::pending`, `HttpWebSocketReceiver::ending`, W4).
- `HttpReceive.responded` is set by `http_response_send_vector ()` whenever cerver tries to send, even if it fails: before the request is completed the rest of it is not handled, and after the dispatch a request without a response is answered with `server_error` (500) and counted in `n_unanswered_requests` (`cerver_http_requests_unanswered_total`).
- The responses are sent with `socket_send_vector_until ()` and `socket_send_file_until ()` of the core (`socket.c`), with one deadline for all the sends of a response (`HttpReceive.send_deadline`, set by its first send, `http_cerver_set_send_timeout_milliseconds ()` or the cerver's `send_timeout` in secs): `sendmsg` with `MSG_DONTWAIT` waits with `poll (POLLOUT)` until the deadline, and `sendfile` runs with the `SO_SNDTIMEO` limited to what is left of it, so the `SO_SNDTIMEO` of a blocking socket never extends it; each piece of a stream has its own deadline. Files and videos share `http_response_send_file_pipe ()`.
- The files of a static path with authentication (`http_static_path_set_auth ()`, `_set_decode_data ()`, `_set_authentication_handler ()`) are authenticated in `on_headers_complete` with the static path that has the file, or with the first protected one when none has it (a missing file answers like a protected one).
- A cerver of the protocol of cerver creates its thpool only with `CERVER_HANDLER_TYPE_THREADS`; a web cerver handles each request in its thpool with POLL, THREADS or EVENTS (`cerver_uses_thpool ()`).
- The event loop (2.1b-15, F3 of `roadmap.md` §4.3) is `CERVER_HANDLER_TYPE_EVENTS`, opt-in and only for `CERVER_TYPE_WEB` (`cerver_start ()` fails with another type or without a thpool); THREADS did not change. It is internal, in `src/cerver/events/` (`internal.h` with its types, test-facing methods `CERVER_PRIVATE` and the rest `CERVER_HIDDEN`): `poller.c` (epoll and an eventfd, the only file that knows the system call), `wheel.c` (the timers: 2^8 slots of 2^8 ms, the clock is given), `loop.c` (an I/O thread: `accept4` in batches, the reads into one buffer, the queue of completed connections, the parked ones, the connections that are kept), `dispatch.c` (who runs the jobs: the thpool, or inline for the tests and the fuzzer) and `group.c` (the loops of a cerver: `cerver_set_io_threads ()`, 1 by default, each one with its listening socket and `SO_REUSEPORT` only when there is more than one; `cerver_set_max_connections ()`, 2^14). `src/cerver/http/core/connection.{h,c}` is the `HttpConnection` of a loop and its states (READ, AUTH, PARKED, DISPATCHED, WRITE, CLOSING): the loop reads and parses without waiting (`http_receive_execute ()`, the parser paused with `HttpReceive::pause`, `HttpReceive::connection` is the mark of a receive of a loop), answers the short responses of cerver (what the socket does not take is kept and written with the poller) and gives the thpool the custom authentication (before the body, `http_receive_headers_authorize ()`, the parser continues with `llhttp_resume ()`) and the request (`http_receive_dispatch ()`); the fd leaves the poller before each handoff, the thread that handled the request also logs it, closes its connection (or its WebSocket goes to its loop after the 101, since the 2.1b-21) and gives its memory back to its loop, and only the result of an authentication and a job that the thpool dropped come back through the queue of completed connections. A full thpool parks the request in its loop (policy `wait`, FIFO, `cerver_set_overload_wait_timeout ()`, 2^5 secs, then 503) or answers 503 (`reject`, at the headers of a request with a body). A stop writes a byte in the stop pipe of the cerver (`Cerver::stop_pipe`, since the 2.1b-18; async-signal-safe, the thread of `cerver_start ()` and the sleeps of the cerver poll its read end), and the drain is `event_loop_group_quiesce ()` → `thpool_drain ()` → `event_loop_group_finish ()`. `decode_data` and the uploads generators run in the I/O thread.
- A connection of a loop that is kept (2.1b-16) has the state IDLE between its requests. The thread of the pool that answered its request gives it to the idle connections of its loop by itself, without the queue and without waking the loop up (`event_loop_idle_enter ()`): the list has its mutex (`EventLoop::idle_mutex`), and the socket is armed inside it to be reported once (`EVENT_INTEREST_ONCE`, `EPOLLONESHOT`). The loop owns the connection again when it takes it out of the list with the same mutex: when it is reported (`event_loop_idle_claim ()`, its source is `silent` from then: it stays registered, so its next handoff to the pool costs no system call and `http_connection_unwatch ()` skips it), when its time ends (the loop checks its idle connections every `EVENT_LOOP_IDLE_SWEEP`, 2^8 ms, while it has any; only the first idle one wakes it up; an idle connection has no timer in the wheel), when a new connection needs its place at the limit (`http_connection_evict ()`, the loop accepts first and handles the connections that were reported before it accepts), or when the loop stops. An idle connection is not in the list of the ones that the loop walks to end them. Only a connection with bytes behind its request (a pipelined one, `HttpConnection::pending`) or of a loop that stops comes back through the queue (`HTTP_CONNECTION_OUTCOME_KEPT`); a request that the loop answers by itself follows `HTTP_CONNECTION_NEXT_KEEP`, and a pipelined one behind it waits for the next step. A connection that is not kept is still ended by the thread of the pool. Never touch a connection after `event_loop_idle_enter ()` returned 0, and never read the state of a connection that the loop did not claim.
- The pools (2.1b-17, F5 of `roadmap.md` §4.5): a web cerver has its default pool (`HTTP_POOL_DEFAULT_NAME`, the thpool of the cerver with its policy and its wait) and the named ones that are created before it starts (`http_cerver_pool_create ()`, `http/core/pool.h` and `pool.c`; `HttpPool` is opaque, its struct is in `src/cerver/http/core/internal.h`; up to `HTTP_CERVER_POOLS_SIZE`, each one with its `Thpool`, started in `http_cerver_init ()`, and its own queue, policy and wait, the ones of the cerver until they are set). A group, an endpoint or a route of the first API chooses its pool by its name (`http_group_set_pool ()`, `http_endpoint_set_pool ()`, `http_route_set_pool ()`; `HTTP_ROUTE_SETTING_POOL` is inherited like the other settings and resolved by `http_tree_resolve_pool ()` when the tree is compiled: a name that no pool has is an error of the tree and the cerver does not start). Only an event loop gives each request to its pool: each loop has a lane for each pool (`EventLane`: its dispatcher and its own FIFO of parked connections, in the position of the pool), the connection chooses its lane every time that it submits a job (`http_connection_pool_select ()`, also for its custom authentication), and a place that a pool frees only wakes the loops with connections parked in that lane (`event_loop_space ()`). The drain is quiesce → `thpool_drain ()` of the thpool → `http_cerver_pools_drain ()` → finish, and `http_cerver_pools_end ()` ends their threads. With the other handler types the named pools do not start (a warning) and the thread of a connection handles its requests. The health and the ready routes (`http_cerver_set_health_route ()`, `http_cerver_set_ready_route ()`) are two dispatches (`HTTP_RECEIVE_DISPATCH_HEALTH`, `_READY`) that are selected before the routes tree with the exact path and GET or HEAD, without an endpoint, and answered like the short responses of cerver: by the loop, also with every thread busy. Ready answers 503 with `Retry-After` and without closing the connection (`not_ready_error`) when a pool with threads is full or has parked requests, or the cerver stops (`http_cerver_is_ready ()`). The metrics of each pool have the label `pool` (`cerver_http_pool_*`, with the histograms `cerver_http_pool_wait_seconds` and `_run_seconds` of its thpool; the `cerver_thpool_*` ones are still the thpool of the cerver without a label). `cerver_http_connection_requests` is the histogram of the requests of each connection that ended (buckets of 2^i up to 2^10): `http_cerver_connection_ended ()` counts a connection once, where its owner ends it (`http_connection_request_release ()` with event loops; `cerver_receive_http_end ()` with threads, never when it goes back to the thpool), the bucket before the total, so a test waits for `HttpCerver::n_connection_requests`. `cerver_http_uploads_write_seconds_total` and `_bytes_total` measure the writes of the files of the uploads (`http_receive_mpart_file_write ()`), that an event loop does by itself. The stats of the admin routes (`cerver/stats`) have `pools`, `connections`, the health counters and the uploads. `test/http/pools.c` runs alone with `POOLS_ONLY=1`; its handlers tell the name of their thread (`thpool-<name>-N`), which is how a test knows the pool that ran a request; `web/pools` is its integration pair, and `benchmarks/server` takes `BENCH_POOL`.
- Connections, sockets, receives and clients are recycled in bounded free-lists (`collections/freelist.c`), with their stats and synchronization values inside them (with the objects of `http/recycle.c`, a GET is 0 allocations and a POST JSON 14, `test/performance.sh`).
- The teardowns join the handlers threads (`handler_stop ()`), wait for the event and error actions that run in their own threads and for the detachable connection threads (`ThreadGroup`, `threads/thread.c`); a drain that times out waits `CERVER_DRAIN_GRACE_TIMEOUT` more seconds and logs what is still alive.
- The default uploads generators add a sequence that the request takes from its `HttpCerver` the first time a generator asks for it: files `fd-time-sequence-index-name`, directories `fd-time-sequence`.
- Vendored third-party code: `http/parser/` (llhttp), `http/json/` (Jansson-derived JSON), `http/jwt/` (libjwt-derived JWT over OpenSSL); `thirdparty.md` lists them with their licenses. They follow the cerver call style (space before call parentheses) but keep their upstream structure otherwise. Since the 2.0b-69 the JWT (`jwt.c`), `json/value.c` and the table of `json/hashtable.c` follow the whole cerver style, and no `goto` is left in the JSON; the names of the rest of `json.c` are the 2.0b-71 (`roadmap.md` §4.3.13). The lookup3 hash of `hashtable.c` and the license headers stay as upstream.
- JWT (2.0b-67): `jwt/key.{h,c}` is cerver's own: a `JwtKey` is created once per algorithm (the HS secret or the `EVP_PKEY` of RS / ES, with its type and curve checked; `jwt_key_check_strength ()`) and signs / verifies (HMAC in constant time, ES with a low S). The `HttpCerver` loads its keys as `JwtKey` in `http_cerver_init` (a key that does not fit the algorithm stops the cerver, `JWT_ALG_NONE` is rejected by the setter) and every bearer goes through `http_cerver_auth_jwt_verify ()` (`auth.c`): `jwt_decode_with_key ()` (the header must name the algorithm of the key), the max size, `exp` / `nbf` with the leeway, `iss`, `aud`. Tokens are parsed strictly (canonical base64url of `utils/base64.c`, objects without repeated keys). The old `jwt_decode ()` with a raw key stays for the upstream tests in `test/jwt/`; `test/http/tokens.c` covers the cerver path.
- JSON (2.0b-67): the hash seed comes from `getentropy ()` (set in `http_cerver_global_init`), a parse can allocate `JSON_PARSER_DEFAULT_MEMORY_FACTOR` bytes per byte it reads (`json_set_parser_memory_factor ()`), the numbers use a "C" `locale_t`, `http_response_json_*` build their bodies with the library (escaped, owned by the response). The internal methods (`hashtable_*`, `utf8_*`, `jsonp_*`) are `CERVER_HIDDEN` (not exported); the `json_*` names stay the ones of Jansson (libauth uses them). `test/json/safety.c` covers it; `json_tests_seed ()` runs first so the seed race is seen by TSan. `cerver/config.h` includes `<stdarg.h>`: its old `va_copy` with `memcpy ()` broke the json pack / unpack of clang in x86-64.
- Hot objects (2.0b-68): `http/recycle.{h,c}` keeps a cache per thread (and shared `FreeList`s) of `HttpResponse` and of buffers in power of 2 classes (2^8 to 2^16), the pattern of `packets.c`; nothing is recycled with `CERVER_RECYCLE_DISABLED` (the sanitizer builds). `http_response_delete ()` recycles the response, its header is written in its `header_buffer` when it fits (never `free ()` `response->header` directly), and its 64 headers are only cleared when `n_headers` says they were used. The body `String` of a request lives in its arena with a recycled buffer (`max_len` is the class size), and the file stats of a request too. `performance.sh` expects GET 0 and POST JSON 14 allocations (the 14 are the handler's `json_loads ()`).

## Conventions

- Comments: the public headers are documented with Doxygen like in `labs` (its `CLAUDE.md`, Conventions): `@file`, a group per module and a subgroup per region, every parameter, return value and field, `@internal` in the headers of `src/`, and only what is verified in the code. `make docs` (`Doxyfile`, `Dockerfile.docs`, the `docs` job of `build.yml`) fails with any warning, and every clang build adds `-Wdocumentation`.
- Code style: tabs, a space before call parentheses (`foo (bar)`) in every file, vendored code included, `#pragma region` blocks to group sections. Exceptions: a function-like macro name in its `#define NAME(x)` can not have a space, and the X-macro tables keep their existing form (`XX(...)` entries, `*_MAP(XX)` inside functions); X-macro arguments are stringified with `#`, so their text must not be changed.
- No literal values inside functions: sizes, lengths, prefixes, separators and timeouts are named constants (`#define` in the header or a `static const` at the top of the source file), e.g. `HTTP_ERROR_BUFFER_SIZE` instead of `char error_buffer[64]`. Applied to new code now; the rest of the codebase is migrated later.
- Keep `if` / `case` bodies short: when a branch needs its own variables or more than a couple of statements, move it to a dedicated `static` function and call it from the branch. Applied to new code now; the rest of the codebase is migrated later.
- Source files have a one-word name (`tree.c`, `compatibility.c`), never `route_compat.c`.
- WebSocket names (A25, 2.1b-21): the identifiers say `web_socket` (`HttpWebSocket`, `http_web_socket_send ()`, `HTTP_WEB_SOCKET_*`), the folders `websockets` (`include/cerver/http/websockets/`, `test/websockets/`, the `websockets` object of the admin stats), and the files, the metrics and the URLs `websocket` (`test/web/websocket.c`, `cerver_websocket_opened_total`).
- `CHANGELOG.md` holds only the current version's changes, grouped under headings (`## HTTP`, `## Tests`, …), one line per commit message.
- Version bumps are a dedicated commit ("Updated version to Beta 2.1b-N") that updates `version.txt`, `include/cerver/version.h` (version, name, date, time), `ARG CERVER_VERSION` in `Dockerfile`, `cerver-install.sh`, and replaces `CHANGELOG.md` with that version's commit messages. `version.txt` and `CERVER_VERSION` must match or the version CI check fails.
- `docs/` is a git submodule (`ermiry/cerver-docs`).

## Branches

- `nightly` is the experimental 2.1 line (llhttp since the 2.1b-8, WebSocket, event loop, keep-alive, named pools, TLS, HTTP/2), planned phase by phase in `roadmap.md`, where it can break the API for a better design (each break in `incompatibilities.md`); its betas go to `nightly-beta` as 2.1b-N ("Nightly Beta"). `http` / `http-beta` is the stable 2.0 line, `core` / `beta` the 1.x line.
- `http` is not merged into `nightly` anymore (since the 2.1b-15; the last merge was the 2.0b-70, in the 2.1b-10): the code of the two lines is different (llhttp, the list of headers, the layout by domains, the event loop), so a fix for the 2.0 is made in `http` and applied here by hand, file by file, with its test, like the ones of the 2.0b-71 and the 2.0b-72 in the 2.1b-12 and the 2.1b-13 (`roadmap.md` §4.12). Nothing goes from `nightly` to `http` until the 2.1 integration. The `merge=ours` entries of `.gitattributes` are not used anymore.
- The gate of a `nightly` beta is the one of `http` plus the long runs of `scheduled.yml` (`roadmap.md` §5), with the HTTP and WebSocket suites in the two models (THREADS and EVENTS).
