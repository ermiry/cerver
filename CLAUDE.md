# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is the branch `labs`, the line 3.0 (betas `3.0b-N` in `labs-beta`): cerver with code that is 100 % of its own, written to beat the best implementations of the industry, see `roadmap.md`. It was born from `nightly` in the 2.1b-13 and it receives nothing by merges: the fixes of `nightly` are ported by hand into the code that `labs` still shares with it, and a module of `labs` that matures can be ported by hand to `nightly`. The code of other projects that is still here is in `thirdparty.md`, each phase removes some of it; the cryptography is never written here, it goes through `cerver/crypto` to its provider. The license is Apache-2.0 (`LICENSE.md`, `NOTICE`).

Cerver is a C11 framework for building servers, built as a shared library (`bin/libcerver.so`). It supports five server types (`CERVER_TYPE_CUSTOM`, `GAME`, `WEB`, `FILES`, `BALANCER`), and a client API for connecting to cervers. The core (everything outside `http/`) is the one of the 1.8 line (branch `core`), ported in 2.0b-63, 2.0b-64 and 2.0b-66 (the whole 1.8: UDP, IPv6, the pools and workers, the portable 32 bytes header with the balancer's route id, the serializer by schema, the histograms and request handlers, game, zero warnings) and in 2.0b-70 (the 1.8.1: the fixes found while documenting the core, `examples/start.c`): `src/` and `include/` outside `http/` are identical to the ones of `core` except the web parts of `cerver.{h,c}` and `handler.{h,c}` (a web cerver never sends the cerver teardown packet into its HTTP connections), and fixes and features of the core land in `core` first and are seeded here. What `http` changed first in files of the core (`config.h`, `utils/base64.{h,c}`) goes back to `core` in the 1.8.2. The integration pairs run in IPv4 and in `::1` (`CERVER_TEST_ADDRESS`, `test/address.h`), new source files of the repo end with a newline. It targets Linux with gcc (uses `_GNU_SOURCE`, pthreads, OpenSSL, `-Wl,-rpath`). On macOS, build and test inside the Docker images (see the Building page of the wiki) rather than natively.

Dependencies: pthreads, OpenSSL (`-lssl -lcrypto`), libm, optionally zlib (`-lz`, with `ZLIB=1`, for the gzip of the HTTP responses), and libcurl (only for the web integration test clients). OpenSSL is the provider of `cerver/crypto` (`include/cerver/crypto/{random,hash,memory}.h`, the provider in `src/cerver/crypto/openssl.c` behind the internal `src/cerver/crypto/provider.h`): the code outside `http/jwt/` never includes OpenSSL, it calls `cerver_crypto_random_bytes ()` (the `getrandom ()` of the kernel), `cerver_crypto_sha1 ()` and `cerver_crypto_cleanse ()`. `http/jwt/` still calls it directly until the JWT of cerver (L2).

## Build

The `makefile` is controlled by variables:
- `TYPE=development` (default; enables all `*_DEBUG`/`*_STATS` defines and `-g`), `test`, `beta`, `production`
- `COVERAGE=1` (only with `TYPE=test`), `NATIVE=1` (`-march=native`), `CC=g++` (the code must also compile as C++11, without `-fpermissive`), `CC=clang`
- `CRYPTO=openssl` (the default and the only provider) defines `CERVER_CRYPTO_OPENSSL` in `DEFINES`; another value stops the build, and `src/cerver/crypto/provider.h` fails without a provider
- `WERROR=1` makes every warning an error (the CI sets it): the library, the tests, the examples, the fuzzers and the benchmarks build with zero warnings in gcc, g++ and clang, in `test` and `development`; `CERVER_ZERO_INITIALIZER` (`config.h`) is the zero initializer of a struct for C and C++, and `CERVER_PRINTF_FORMAT` marks the functions with a format
- `ZLIB=1` defines `CERVER_ZLIB` and links zlib; without it the compression settings are accepted and nothing is compressed (`http_compression_available ()`). `Dockerfile.test`, `Dockerfile.fuzz` and `test.yml` build with it; in `build.yml` gcc builds without it and g++, clang, valgrind and the sanitizers with it, so both paths compile and the units of permessage-deflate run under each of them

```sh
make                    # build bin/libcerver.so
make examples           # build examples/bin/* against bin/libcerver.so
make test               # build all tests: objs, test app lib, units, integration, testhandler
make clean
make install            # copy libcerver.so to /usr/local/lib and headers to /usr/local/include
```

`compile.sh` cleans and builds the library with the development flags. Keep code compiling with zero warnings under gcc, g++ and clang, with the warning flags in `COMMON` (`-Wpedantic -pedantic-errors` for C), and every `.c` / `.h` that is touched ends with a newline. The Dockerfiles use `gcc:16.2` and `debian:trixie-slim` (`Dockerfile.fuzz` and the `clang` job of `build.yml` use `debian:trixie`), and the workflow jobs that compile on the runner use `container: gcc:16.2` (the sanitizers run in a `docker run` of that image, because TSan needs the host's `sysctl`).

The HTTP parser is llhttp 9.4.3 (since the 2.1b-8, phase F2 of `roadmap.md`), split in `include/cerver/http/parser/{llhttp,helpers,api}.h` and `src/cerver/http/parser/{llhttp,api,http}.c`. `llhttp.c` is generated by llparse and was restyled with a verified script (the same `objdump -d` before and after): an update of llhttp is seeded again with that script, never edited by hand; `api.c`, `http.c` and the headers are edited by hand. The parser is internal since the 2.1b-12: its API is `CERVER_HIDDEN` and the objects of `http/parser/` are compiled with `-fvisibility=hidden` (`PARSEROBJS` in the `makefile`), so `libcerver.so` exports no `llhttp` symbol; code outside the library reads the fields of `HttpReceive.parser`, and `benchmarks/http-parser.c` links the objects of the parser. `thirdparty.md` lists the vendored code and its licenses.

Run an example: `LD_LIBRARY_PATH=bin/ ./examples/bin/start server` (and `start client` in another terminal), or `LD_LIBRARY_PATH=bin/ ./examples/bin/web/web`. A failed `cerver_start ()` is released with `cerver_teardown ()`, never with `cerver_delete ()`.

## Tests

There is no test framework; `test/test.h` provides `test_check_*` macros that print the location and `exit(1)` on failure. Each unit test binary has a `main` that calls static `test_*` functions.

```sh
make TYPE=test -j4 && make TYPE=test -j4 test
bash test/run.sh                 # run all unit test binaries
./test/bin/http                  # run a single unit test binary (e.g. http, json, jwt, collections, utils, threads)
```

Run test binaries from the repo root — they reference relative paths such as `./test/http/keys/key.key` and `version.txt`.

How tests are linked (see the `units`, `integration-*` and `testhandler` targets in `makefile`):
- Most unit binaries link all objects from a subdirectory, e.g. `test/http/*.o` → `test/bin/http`. Adding a new `.c` file to such a directory automatically includes it; register its test functions from that directory's main file (e.g. `test/http/http.c`). New top-level test binaries need a line in `units` and in `test/run.sh`.
- `test/bin/crypto` (`test/crypto/`) checks `cerver/crypto`: the random bytes, SHA-1 with the vectors of FIPS 180 and the accept of RFC 6455, and the cleanse.
- `test/bin/faults` (`test/faults/`) is built only without `SANITIZER` and `test/run.sh` runs it only without `RUNNER`: `test/faults/faults.c` defines `malloc`, `calloc`, `realloc` (over the `__libc_*` allocators of glibc) and `pthread_create` (over the next one, `dlsym (RTLD_NEXT)`) in the binary, so the calls of `libcerver.so` resolve to them, and a test arms the next call of one of them to fail (`faults_arm ()`: in any thread or only in its own, and for an allocation only one of a size). Its tests are the paths that only a failure of the system reaches: the frames that came with the 101 of a client without memory, the thread of a client or of a WebSocket of the server that is not created. A first cerver of the process opens the reserve fd of `accept ()` (`handler.c`), that stays open: the fds are counted after it.
- `test/app/` is built into `test/bin/app/libapp.so`, a shared test application (handlers, routes, users, auth) linked by the HTTP unit tests and the integration servers.
- Integration tests are server/client pairs: servers in `test/cerver/` (TCP, port 7000) and `test/web/` (HTTP, port 8080), clients in `test/client/` and `test/client/web/` (libcurl). `bash test/integration.sh [pair ...]` builds `Dockerfile.test` (`SANITIZER=address,undefined` or `thread` builds a sanitized image) and runs each pair with `test/pair.sh` inside one container: the server and the client run together, with a readiness probe, deadlines, gdb stacks on a hang and both exit codes checked. `test.sh` and `.github/workflows/test.yml` use it.
- The clients wait by condition with `test_wait_counter ()` (`test/test.h`), never with fixed sleeps; counters written by other threads use `test_counter_add ()`.
- `test/cerver/core.c` (`test/bin/cerver/core`) is a TCP cerver in the same process: dispatch with POLL and THREADS, multiple handlers, auth, inactive clients, update threads, teardown with connected clients and the cerver events. `test/client/lifecycle.c` covers the client connections against a fake cerver (async connects, reconnection, many clients).
- `bash test/repeat.sh <test/bin/... | pair> [count]` is the flaky hunter: it repeats a binary or a pair in the test image, saves gdb stacks if something hangs and leaves the logs of the run that failed in `repeat-artifacts/` (`ARTIFACTS`). `test_run ()` (`test/test.h`) prints the name of each test before it runs it. `RUNNER="valgrind ..." bash test/run.sh` runs the unit tests under valgrind.
- `test/load/routing.c` (in `test/bin/load`, with the units of `test/load/balancer.c`) is a balancer in the same process with two real services (round robin, handler id, reconnection, a 1 MB packet, no services), `test/client/features.c` covers the 1.x client features (states, async connect, send queue, reconnection), `test/network/socket.c` and `test/network/network.c` (in `test/bin/network`, with `test/network/udp.c`) the sends with deadline and the addresses, and the `balancer/*` and `cerver/queue` pairs run in `integration.sh`. The process pairs `balancer/{reconnect,large,unavailable,concurrent,abandon}` put the balancer (`test/cerver/load.c`) in front of two `test/cerver/upstream.c` services, restarted by `test/supervise.sh` when the client asks one to stop, with the clients of `test/client/load/` (`balancer.c` has their common code). `bash test/allocations.sh` counts the core allocations per connection (POLL, THREADS) and per packet of a handler with its own queue. A build with `SANITIZER` (and the fuzzers) defines `CERVER_RECYCLE_DISABLED`, so the free-lists do not hide a use after free.
- Fuzzing: `test/fuzz/*.c` are libFuzzer targets (`request`, `lenient` (the requests with the lenient flags of the parser), `pipeline` (the requests of a connection that is kept, with `http_receive_reset ()` between them and the receive prepared with an arena), `multipart`, `url`, `json`, `jwt`, `tree`, `frame` and `handshake` (WebSocket), and the core ones `receive`, `packet`, `client`, `file`, `datagram`, `address`, `serializer`, `game`) built with `make TYPE=test CC=clang fuzz` in `Dockerfile.fuzz`; `SECONDS_PER_TARGET=30 bash test/fuzz.sh [target ...]` runs them from the seeds in `test/fuzz/corpus/` and leaves crashes in `fuzz-artifacts/`; they are built with `-fno-sanitize-recover=undefined`, so the first undefined behavior that UBSan finds fails its target. The second byte of the input of `frame` is the compression that was negotiated (the peer that resets its context, the window bits). The long fuzzing of `scheduled.yml` is a job for each target.
- `bash test/performance.sh` (needs valgrind) fails on allocations per request above the current ones (the ones of 1024 requests after 256 of warm-up, counted without rounding: GET 0, POST JSON 14), a server that ends with an error or that has to be killed, load errors or 503s, req/s below half of `benchmarks/baseline.txt` for the architecture, or a routes tree less than 2x faster than the 2.0b-58 matcher on the synthetic tables of `benchmarks/routes/` (made by `benchmarks/generate.py`). `bash test/nginx/run.sh` runs the `test/web/features.c` server behind nginx (`NGINX_IMAGES`, by default the version of production, 1.31.6, and the stable one, 1.30.6), with an upstream `keepalive`, the forwarded headers and a location without buffering: the `test/client/web/features.c` client with `FEATURES_PROXY=1` (the same client of the standalone `web/features` pair) and then the load, failing on any 502 or upstream reset.
- `test/http/features.c` is a web cerver in the same process for the headers that cerver adds (Date, X-Request-Id, CORS, Vary), ETag / 304, gzip, streams, chunked bodies with trailers, the client's address and the metrics; `test/http/responses/{date,conditional,compression}.c` and `test/http/security/proxy.c` are their units.
- `test/http/disconnect.c` (2.0b-65) is a web cerver in the same process whose raw clients leave in every part of the process in four ways (a close, a reset, a half-close and vanishing): the requests cut at each byte (the expected stage comes from the rules of the parser), the handler that asks for its client's state (also from the thread of a worker), the large responses cut after some bytes (gzip included), the statuses that are not 200 (304, 404, 405, 500, 401, 413), a `recv` interrupted by a signal, the queue, the pipeline, the 503 and the drain. After each batch the counters must change exactly (`n_aborted_requests[stage][reason]`, `n_vanished_requests[stage]`, `n_failed_responses`), the fds must be the ones it had and the uploads path must be empty. `test/run.sh` runs a sample (`DISCONNECT_LEVEL=sample`, the seed is printed, `DISCONNECT_SEED` repeats it); `bash test/disconnect.sh` runs every offset with `DISCONNECT_ONLY=1` in the normal, ASan+UBSan and TSan images (valgrind with the sample) in both families. Behind nginx, `test/web/disconnect.c` and `test/client/web/disconnect.c` run in the three configurations of `test/nginx/` (`CONFIGS`: `direct` with HTTP/1.1 and an unbuffered location, `services` with HTTP/1.0 and buffering, `pair` with two instances, one of them crashing on `/crash`).
- `test/bin/websockets` (`test/websockets/`) has the units of the text, the frames (split at every byte), the messages (the close codes), the handshake and permessage-deflate (the examples of RFC 7692 sections 7.2.3.1, 7.2.3.2 and 7.2.3.4, a message that is cut, a decompression bomb), and two suites in the same process: `server.c` (a web cerver with raw clients of `raw.c`: the rejections of an upgrade one by one with the places that they give back, what `on_upgrade` decides and the headers that it adds to the 101, echoes of every size, frames with the request, fragments, both closes, each protocol error with its code, abrupt clients, ping / pong and `on_ping` / `on_pong`, 8 threads sending to one connection, rooms and their limits, broadcast, a slow reader, the limit, the teardown with clients that answer its 1001 and with clients that do not, the settings that a group gives to its subgroups and endpoints, streaming, compression, metrics and stats, and the fds after each server) and `client.c` (the public client against a cerver and against fake servers that answer wrong on purpose, the reconnection and the ways it ends, the messages of 8 threads checked one by one). The short timeouts of both use `test_milliseconds ()` (`test/test.h`): `TEST_TIME_SCALE` multiplies them, 4 in a build with a sanitizer and under the `RUNNER` of `test/run.sh`. The `frame` and `handshake` fuzzers cover the receiver and the handshakes. `bash test/autobahn/run.sh` runs autobahn-testsuite (`crossbario/autobahn-testsuite:25.10.1`, amd64) against the server (`test/web/autobahn.c`) and the client (`test/client/web/autobahn.c`) and fails on any case that is not OK, NON-STRICT or INFORMATIONAL, and on a report that does not have its 517 cases (`test/autobahn/check.py`); `web/websocket` is a pair, also behind nginx (`/websocket/`); `test/performance.sh` checks 0 allocations per WebSocket message (`benchmarks/messages.c`).
- `.github/workflows/scheduled.yml` (`workflow_dispatch`, dispatched by the cron of `master`) runs the TSan pairs, the flaky hunter, long fuzzing, performance, nginx, the disconnect matrix and autobahn with the sanitizers. The jobs run in `container: gcc:16.2`, the test ones with `--sysctl net.ipv6.conf.all.disable_ipv6=0` for the IPv6 tests.
- The routes tree is covered by `test/http/routes/tree.c` (match table, registration errors, inheritance, middlewares, compatibility, group roots, admin routes in groups, the routes json, fuzz) and end to end by `test/http/receive.c` and the `test/web/router.c` pair. `make tree` builds `benchmarks/bin/tree`.
- The parser is covered by the `parser` region of `test/http/receive.c` (the methods of llhttp, each strict difference with http_parser rejected and accepted with its lenient flag, the protocols and the versions that are not served, what is rejected with every flag, upgrades, keep-alive and pipelining, the always active headers limit) and by the `request` and `lenient` fuzzers; `benchmarks/http-parser.c` measures llhttp alone (`make bench`) and, like `benchmarks/frames.c`, exits with 1 when what it measures did not happen (every request completed, every message as it was sent). `make bench tree load` builds in `build.yml` with the three compilers; `NATIVE=1` only adds `-march=native`.
- `bash benchmarks/competitors/run.sh` measures the JSON and the parser of cerver against their competitors (yyjson, simdjson, Jansson, RapidJSON; llhttp, picohttpparser): `Dockerfile.competitors` builds each one from its source at a fixed version (its `ENV`), `benchmarks/competitors/build.sh` builds a binary for each implementation (Jansson and llhttp have the names of the copies of cerver) with a driver of its module (`json/driver.c`, `parser/driver.c`, with the documents and the requests generated in them) and `measure.c`, that counts the allocations (it defines the `malloc ()` family of the binary) and takes the median of 5 runs. The results go to `benchmarks/competitors/results/<architecture>.txt`; they only count from a machine without other load. `make bench` does not build `benchmarks/competitors/`.
- `test/bin/version` checks that `CERVER_VERSION` in `include/cerver/version.h` matches `version.txt` (run by CI on `master`/`*beta`).
- The unit tests mirror `src/cerver/`: a folder for each module with one binary (`test/bin/connection`, `handler`, `load`, `network`, `packets`, `files`, `system`, …), whose main is the file with the name of the folder (or the module, `test/load/balancer.c`) and calls the `*_tests ()` of the other files of the folder, declared in the header of the folder (`test/network/network.h`). `test/http/` has the subfolders of `src/cerver/http/` (`core`, `headers`, `requests`, `responses`, `routes`, `security`) in the same `test/bin/http`; its suites in the same process (`http.c`, `server.c`, `features.c`, `disconnect.c`, `receive.c`) stay on top. The integration pairs, the app, the fuzzers, the examples and the benchmarks are not mirrors; the handler pair is `cerver/handler` (`test/cerver/handler.c` and `test/client/handler.c`).

Coverage: `bash coverage.sh` (builds with `TYPE=test`, runs units, then `make coverage`).

## Architecture

Headers live in `include/cerver/` and mirror `src/cerver/` one-to-one (`src/cerver/http/routes/route.c` ↔ `include/cerver/http/routes/route.h`). Public functions are marked `CERVER_EXPORT` (`config.h`) and declarations are wrapped in `extern "C"`.

The layout (3.0b-2, the old paths are in `roadmap.md` §11): on top only `config.h`, `version.h` and the umbrella `cerver.h`; the core in `core/` (the `Cerver`: `cerver`, `types`, `info`, `data`, `handler`, `start`, `update`, `end`, `report`, `serialization`), `admin/` (`admin`, `cerver`, `stats`, `lifecycle`, `handler`, `poll`), `auth/` (`auth`, `hold` with the connections on hold, `sessions`), `client/` (`client`, `events`, `connect`, `requests`, `handler`), `connection/` (`connection`, `stats`, `recycle`, `data`, `lifecycle`, `end`, `registry`, `update`, `send`), `files/` (`files`, `cerver`, `images`, `send`, `receive`), `handler/` (handler, receive, events, errors), `load/` (the balancer: `balancer`, `stats`, `service`, `events`, `start`, `route`, `end`), `network/` (network, socket, udp), `packets/` (`packets`, `header`, serializer), `system/` (system, timer, input), plus `collections/`, `crypto/`, `game/` (`types` is the game types), `threads/`, `types/` and `utils/`; HTTP in `http/core/` (the `HttpCerver`: `http`, `pairs`, `public`, `routes`, `uploads`, `limits`, `settings`, `stats`, `admin`, `callbacks`, `forms`, `handler`, `upgrade`, with `custom`, `metrics` and `utils`), `http/headers/` (`fields` is the list `HttpHeaders`, `types`, `header`, `buffer`), `http/requests/`, `http/responses/`, `http/routes/` and `http/security/`, plus `json/`, `jwt/`, `parser/` and `websockets/`. The files have one word. The main header of a module has its types and its parts include it; it never includes its parts (the includes are only at the start of a file), so a file includes the parts that it uses. `<cerver/cerver.h>` is the umbrella of the core and `<cerver/http/http.h>` the one of HTTP, with every part; they only include. The functions that find or act on something by a key are named with `_with_` (`client_get_with_sock_fd ()`, `http_headers_find_with_name ()`), never `_by_`.

Inside the library (`include/` and `src/`) every include of cerver uses quotes (`"cerver/core/cerver.h"`); the tests, the examples and the benchmarks use the installed form `<cerver/...>` and quotes for the internal headers that they read. The includes are at the start of a file, in blocks separated by an empty line and sorted by their path inside each block: the C standard library; the system (`pthread.h`, `unistd.h`, `sys/*`, `netinet/*`, …); the specialized libraries (OpenSSL, zlib, curl, the SIMD intrinsics); `cerver/types/`; `cerver/collections/`; the files on top (`config.h`, `version.h`); the core of cerver (`admin`, `auth`, `client`, `connection`, `core`, `files`, `handler`, `load`, `network`, `packets`, `system`, with their `internal.h`); a block for each package (`crypto`, `game`, `http` with every one of its folders, `threads`); `cerver/utils/`; and the local ones of the tests and the examples. An include inside an `#ifdef` stays where it is.

`include/` has only what is installed. What is internal lives next to its `.c` in `src/` (found with `-I src`): the headers that are internal as a whole (`http/core/{access,recycle}.h`, `http/routes/compatibility.h`, `crypto/provider.h`) and the `internal.h` of a folder with what its files share (`admin/`, `auth/`, `client/`, `connection/`, `core/`, `files/`, `load/`, `packets/`, `http/core/`, `http/headers/`, `http/responses/`, `http/websockets/`). A method that the parts of a split file share is `CERVER_HIDDEN` there, so `libcerver.so` exports the same symbols; an internal header never has the relative path of a public one. `http/json/` and `http/parser/` are still installed until L1 and L3 replace them (`HttpReceive` embeds the `llhttp_t`).

Enums and their string conversions are generated with X-macro `*_MAP(XX)` tables — extend the map rather than the enum directly.

Core flow:
- `cerver.c` — `Cerver` lifecycle (create, configure, start, teardown) and its handler type: `CERVER_HANDLER_TYPE_POLL` (single thread with `poll()`) or `THREADS` (thread per connection). A thread pool is also used for handlers.
- `client.c` / `connection.c` — a `Client` owns one or more `Connection`s; the same structures are used server-side for connected clients and in the client API for connecting to a cerver.
- `receive.c` → `packets.c` → `handler.c` — bytes are received per socket, assembled into `Packet`s (typed by `PacketType`), and dispatched to cerver-level handlers (`app_packet_handler`, `app_error_packet_handler`, `custom_packet_handler`). `Handler`s can run in dedicated threads with their own job queue.
- `auth.c`, `sessions.c`, `admin.c` — optional authentication, session ids, and an admin cerver for managing clients.
- `game/` — lobbies, players, game types for the game server template.
- `threads/` — `thpool` (bounded ring buffer queue, joinable threads, `thpool_drain`, overload `wait`/`reject`), `jobs` (job queues), `worker`, `bsem`, thread helpers (every thread created by cerver blocks SIGINT/SIGTERM).
- `collections/` — `dlist`, `avl`, `htab`, `pool`, `queue`, `arena` used throughout instead of external containers.
- Lifecycle: `cerver_stop_request` (EINTR in accept/poll = stop; a request before `cerver_start` cancels it, `stop_requested`, so a cerver is started once), `cerver_teardown` drains the thpool before releasing anything; the state shared by the HTTP cervers of a process (jwt pool, responses producer, common responses, multi-parts pool) is created by the first one that starts and released by the last one that ends (`http_cervers` in `http.c`), the producer follows a cerver that is still alive; web worker threads keep a `HandlerThreadContext` (arena + buffers) and the request data lives only during its handler.
- `receive.c` — `receive_handle_buffer` assembles TCP packets split between `recv ()` calls, shared by the cerver and the client.
- `types/string.c`, `utils/` (log, base64, sha256, misc) — shared helpers.

HTTP layer (`http/`), used when the cerver type is `CERVER_TYPE_WEB`:
- `http.c` — `HttpCerver` attached to a cerver: routes tree, static paths, uploads config, JWT keys/alg, origins whitelist, default response headers, custom data, stats; the parser callbacks select the endpoint in `on_headers_complete` (match, method, auth) and dispatch it in `on_message_complete` (endpoint, automatic OPTIONS, opt-in 405, 308 redirect or catch all). The `llhttp_t` is embedded in `HttpReceive` with its own settings; the url is closed in `on_url_complete` and each header in `on_header_value_complete`; a callback that rejects returns `HTTP_RECEIVE_PARSER_STOP`; `on_message_complete` returns `HPE_PAUSED` (one request per connection) and keeps `keep_alive_requested` and `unparsed` for the keep-alive of F4. Strict by default, `http_cerver_set_parser_lenient ()` (`HttpParserLenient`, without the header value relaxed flag of llhttp, that loops forever with a NUL). The url and headers limits are always active.
- `method.h` — the only table of methods (`REQUEST_METHOD_MAP`, the values of llhttp: 34 HTTP methods and `QUERY`, `REQUEST_METHOD_SIZE` 47, `REQUEST_METHOD_UNDEFINED` 255), all of them can be registered; the methods of RTSP are rejected by the parser (400) and `PRI` by its version (505), a method without endpoint is 405 or the catch all. Only `HTTP/1.0` and `HTTP/1.1` are served (2.1b-13): `on_protocol` / `on_protocol_complete` answer a request line of RTSP or ICE with 400, `on_version_complete` another version of HTTP with 505 (`HTTP_PARSER_LENIENT_VERSION` serves any); a `Transfer-Encoding` that does not end with `chunked` (`http_receive_body_has_no_end ()`) and a NUL in a header value are 400 also with their lenient flags.
- `tree.c` — the routes API: `HttpGroup` (prefix and settings inherited by its subgroups and endpoints), `HttpEndpoint` (a handler for a `(path, method)` with its own auth, custom data, modifier, max body, CORS, etag, compression and middlewares) and the radix tree of segments built in `cerver_start` (`http_tree_compile`). The match never allocates and the priority is always static > param (validated ones first) > wildcard, with backtracking, whatever the registration order. Registration errors stop the cerver. `http_group_root_add (group, method, handler)` adds the endpoint of the group's own path (pycerver: `HttpGroup.create / subgroup (prefix, method, handler, **settings)`), and `http_cerver_routes_generate_json` dumps the compiled endpoints (method, path, auth, modifier, compatibility, cors, etag, compression) for tests. A cerver without routes of the first API gets the admin routes as endpoints of its first top level group (`http_cerver_admin_group_init`), added only once (`admin_routes_ready`) by `cerver_start` or `http_cerver_routes_compile`.
- `compatibility.c` — translates the first routes API (`HttpRoute` from `route.c`: `http_route_create`, `http_route_child_add`, `http_cerver_route_register`) into endpoints when the cerver starts; a conflict there is only a warning. Deprecated, removed in 3.0.
- `middleware.c` / `validator.c` — `before` / `after` middleware chains (cerver → groups → endpoint) and the route param validators (`:id<objectid>`, `int`, `uuid`, custom).
- `request.c` / `response.c` / `headers.c` / `multipart.c` / `url.c` / `origin.c` / `admin.c` / `auth.c` — request parsing (params are slices of the url, decoded on demand; custom headers live in the request arena; header names are found with a hash table; the request id and the client's address are resolved in `on_headers_complete`; the query and the values of a form are split by `&` and `=` and then each key and value is decoded in its own memory, `http_query_pairs_decoded ()`; a `Range` is one that starts at a position or the one of the last bytes, `bytes=-N` with `HTTP_RANGE_TYPE_SUFFIX`, and `http_request_get_bytes_range ()` ignores the rest; since the 2.1b-13 the target of a request in absolute form is routed by its path and its fragment is dropped (`http_receive_close_url ()`), the spaces after the value of a header are removed, a repeated header is joined in memory that grows by `HTTP_HEADER_VALUES_GROWTH` with its capacity in `String.max_len`, the trailers of a chunked body and the extensions of its chunks count for the limits of the headers (`http_receive_handle_discarded ()`), the value of a custom header is limited by `http_cerver_set_max_custom_header_size ()` and the default request timeout is 300 secs), responses, multipart uploads, CORS origins, HTTP admin routes (with `cerver/metrics`), JWT auth.
- A response is structured since the 2.1b-11 (F1 of `roadmap.md`): `HttpResponse` is its status and a `HttpHeaders` (`http/headers/fields.{h,c}`: the headers in the order they were added, a name can be repeated and can be any token, each one kept as its line `Name: value\r\n`, 32 fields and 512 bytes inside the list and its own memory up to 256 fields and 16 KiB; a value with CR, LF or NUL is rejected). `http_response_header_set / _add / _remove / _count / _get ()` and their `_with_name` are the API, the older `http_response_add_header ()` and friends keep replacing the header of their type. `http_response_compile_header ()` is the only serializer (status line, `Server`, the headers of the response, the ones of the cerver that it does not have, the empty line); `header` / `res` are the cache of the HTTP/1.1 form and a header or a status that changes discards them; a header set as bytes (`http_response_set_header ()`, `header_is_raw`) is sent as it is. Never write the bytes of a header by hand.
- Every response goes through `http_response_send_message ()` (`response.c`): one `sendmsg` of four parts, the compiled header without its empty line, the headers that cerver adds for the request (a `HttpHeaders` in the stack: `Connection: close` when the connection is closed after it and the response has no `Connection` of its own, `Date`, `X-Request-Id`, `Access-Control-Allow-Origin` + `Vary` of an endpoint with `cors`, `ETag`, `Content-Encoding`), the empty line and the body, without the body for a HEAD. A header that the response already has is not added (`http_response_message_find ()` looks in its headers and in the ones of the cerver, or in its bytes when only they are known), and nothing is allocated (`test/performance.sh` counts it). `HttpReceive.framed` says that the response that was sent has an end without the close of the connection (a Content-Length, a status without body, a HEAD, the last chunk of a stream, a whole file), the condition of the keep-alive of F4. With the endpoint's `etag` a GET is answered with 304 when its If-None-Match matches, and with `compression` the body is gzipped into the request arena. Both choose their headers in the lists of the response and of its cerver since the 2.1b-13 (`HttpResponseFilter`: every header but the Content-Length of the plain body, or only the ones that a 304 keeps; `http_response_message_header ()` writes them again in the arena and `http_response_message_find ()` does not find the ones that the filter dropped); the lines of a header are only read when it was set as bytes.
- `date.c` (the IMF-fixdate cached per thread and second), `conditional.c` (entity tags, If-None-Match / If-Modified-Since), `compression.c` (Accept-Encoding, compressible types, gzip with zlib's memory in the arena), `stream.c` (`http_response_stream_begin / write / end`: chunked to HTTP/1.1, close delimited to 1.0, ended by cerver after the handler), `proxy.c` (`HTTP_TRUSTED_PROXIES_MAP`: none by default, a CIDR list, the private networks or all; X-Forwarded-For from right to left, then X-Real-IP), `metrics.c` (the Prometheus text of the cerver and of every endpoint, with the latency histogram of `HttpRouteStats`).
- cerver closes the connection after a response and the response says `Connection: close` (the 502 behind nginx), added when it is sent (never compiled in a header); the 101 of an upgrade hands the connection to its WebSocket instead. Keep-alive waits for the event loop (F3 / F4), but its pieces are ready: what belongs to a request is separated from what belongs to its connection. A `HttpReceive` lives in the memory of its owner (`HandlerThreadContext.http_receive` in a worker thread, never in the arena of its request) with the resources that it lends (`HttpReceiveResources`, `http_receive_prepare ()`); `http_receive_reset ()` ends a request (uploads, request, deleters, arena, parser with `llhttp_reset ()`) and starts the next one of the connection, no production code calls it yet; the clock, the received bytes, the `recv ()` diagnostics and the headers / request deadlines are fields of the receive, and `http/core/access.{h,c}` (`http_access_request ()`) logs and counts a request when it ends, called once per request by `cerver_receive_http ()` before the WebSocket hand-off, `http_receive_delete ()` and the `arena_reset ()`. `test/http/receive.c` has the regions `framed` and `reset` (many requests through one receive, with the arena and without it).
- `websockets/` (2.1b-9, F6a of `roadmap.md`; the folders of the packages are named in plural) is WebSocket (RFC 6455 and permessage-deflate, RFC 7692) on the threads model: `text.c` (incremental UTF-8), `frame.c` (encoder and incremental parser), `message.c` (the rules of the messages without sockets: fragments, close codes, limits, streaming), `handshake.c`, `deflate.c` (only with `ZLIB=1`, a window of 2^8 for the compressor of cerver is declined), `settings.c` (inherited by the groups one by one, `HttpRouteSettings.web_socket`), `websocket.c` (`HttpWebSocket`: references, its thread with `poll` on its socket and an `eventfd`, the sends with a `send_mutex` per frame and a `message_mutex` per message, the close, ping / pong), `registry.c` (`HttpCerver.web_sockets`: the limit with places reserved before the 101, rooms, broadcast, stats) and `client.c` (`HttpWebSocketClient`, with reconnection). The upgrade is checked in `on_headers_complete` (400 / 426 / 403 / 503) and answered in `on_message_complete` (before middlewares, `on_upgrade`, a raw 101); `cerver_receive_http` hands the connection to a thread of `connection_threads` (`http_web_socket_start`), and the drain sends 1001. A route of the first API with the modifier is still 501. wss:// waits for TLS (F8). Since the 2.1b-12: a stream that does not begin (`http_web_socket_send_begin ()` returns 1) holds nothing and is never ended; a frame that the connection does not take because it is closing is an error of the send that never calls `http_web_socket_fail ()` (only a write that was attempted and failed does); the deadline of a send is created after `message_mutex` is taken; the subprotocols are tokens (`http_header_name_is_valid ()`), and the methods that only cerver calls are `CERVER_HIDDEN`. Since the 2.1b-13: `HttpWebSocket`, `HttpWebSocketClient`, the registry, the handshake and the response of the client are opaque, their definitions and the hidden methods live in `src/cerver/http/websockets/internal.h` (not installed, found with `-I src`; a test that reads a field includes it), the counters are read with `http_cerver_web_socket_get_stats ()` / `http_web_socket_get_stats ()` (`HttpWebSocketStats`), the timeouts in milliseconds have the `_milliseconds` suffix, `on_upgrade` adds headers to the 101 with `http_web_socket_upgrade_add_header ()` (`HttpWebSocketUpgrade.headers`, a `HttpHeaders` in the stack of the upgrade; the 101 is sent in three parts) and the connection keeps the query of its request (`http_web_socket_get_query ()`). The methods of a connection are serialized by connection and their thread is not part of the API. A frame length that is not the shortest one is a 1002, a key that is not canonical a 400; a compressed message must end between two blocks, a block with BFINAL restarts the inflater with its window (`inflateResetKeep ()`), and `http_web_socket_deflate_decompress ()` returns `HTTP_WEB_SOCKET_INFLATE_INVALID` (1007), `_STOPPED` or `_FAILED` (1011). A message that the connection refuses because it is closing never fails it; a connection ends its writes with `SHUT_WR` and a bounded drain (`http_web_socket_end_writes ()`). In the client, `http_web_socket_client_running` (thread local) makes `wait` and `delete` safe inside its own methods, the waits of an attempt watch `wake_fd` (`http_web_socket_client_wait_socket ()`), and the backoff is `http_web_socket_client_backoff_delay ()`.
- `HttpReceive.responded` is set by `http_response_send_vector ()` whenever cerver tries to send, even if it fails: before the request is completed the rest of it is not handled, and after the dispatch a request without a response is answered with `server_error` (500) and counted in `n_unanswered_requests` (`cerver_http_requests_unanswered_total`).
- The responses are sent with `socket_send_vector_until ()` and `socket_send_file_until ()` of the core (`socket.c`), with one deadline for all the sends of a response (`HttpReceive.send_deadline`, set by its first send, `http_cerver_set_send_timeout_milliseconds ()` or the cerver's `send_timeout` in secs): `sendmsg` with `MSG_DONTWAIT` waits with `poll (POLLOUT)` until the deadline, and `sendfile` runs with the `SO_SNDTIMEO` limited to what is left of it, so the `SO_SNDTIMEO` of a blocking socket never extends it; each piece of a stream has its own deadline. Files and videos share `http_response_send_file_pipe ()`.
- The files of a static path with authentication (`http_static_path_set_auth ()`, `_set_decode_data ()`, `_set_authentication_handler ()`) are authenticated in `on_headers_complete` with the static path that has the file, or with the first protected one when none has it (a missing file answers like a protected one).
- A cerver of the protocol of cerver creates its thpool only with `CERVER_HANDLER_TYPE_THREADS`; a web cerver handles each request in its thpool with POLL or THREADS (`cerver_uses_thpool ()`).
- Connections, sockets, receives and clients are recycled in bounded free-lists (`collections/freelist.c`), with their stats and synchronization values inside them (with the objects of `http/core/recycle.c`, a GET is 0 allocations and a POST JSON 14, `test/performance.sh`).
- The teardowns join the handlers threads (`handler_stop ()`), wait for the event and error actions that run in their own threads and for the detachable connection threads (`ThreadGroup`, `threads/thread.c`); a drain that times out waits `CERVER_DRAIN_GRACE_TIMEOUT` more seconds and logs what is still alive.
- The default uploads generators add a sequence that the request takes from its `HttpCerver` the first time a generator asks for it: files `fd-time-sequence-index-name`, directories `fd-time-sequence`.
- Vendored third-party code: `http/parser/` (llhttp), `http/json/` (Jansson-derived JSON), `http/jwt/` (libjwt-derived JWT over OpenSSL); `thirdparty.md` lists them with their licenses. They follow the cerver call style (space before call parentheses) but keep their upstream structure otherwise. Since the 2.0b-69 the JWT (`jwt.c`), `json/value.c` and the table of `json/hashtable.c` follow the whole cerver style, and no `goto` is left in the JSON; the names of the rest of `json.c` are the 2.0b-71 (`roadmap.md` §4.3.13). The lookup3 hash of `hashtable.c` and the license headers stay as upstream.
- JWT (2.0b-67): `jwt/key.{h,c}` is cerver's own: a `JwtKey` is created once per algorithm (the HS secret or the `EVP_PKEY` of RS / ES, with its type and curve checked; `jwt_key_check_strength ()`) and signs / verifies (HMAC in constant time, ES with a low S). The `HttpCerver` loads its keys as `JwtKey` in `http_cerver_init` (a key that does not fit the algorithm stops the cerver, `JWT_ALG_NONE` is rejected by the setter) and every bearer goes through `http_cerver_auth_jwt_verify ()` (`auth.c`): `jwt_decode_with_key ()` (the header must name the algorithm of the key), the max size, `exp` / `nbf` with the leeway, `iss`, `aud`. Tokens are parsed strictly (canonical base64url of `utils/base64.c`, objects without repeated keys). The old `jwt_decode ()` with a raw key stays for the upstream tests in `test/jwt/`; `test/http/security/tokens.c` covers the cerver path.
- JSON (2.0b-67): the hash seed comes from `getentropy ()` (set in `http_cerver_global_init`), a parse can allocate `JSON_PARSER_DEFAULT_MEMORY_FACTOR` bytes per byte it reads (`json_set_parser_memory_factor ()`), the numbers use a "C" `locale_t`, `http_response_json_*` build their bodies with the library (escaped, owned by the response). The internal methods (`hashtable_*`, `utf8_*`, `jsonp_*`) are `CERVER_HIDDEN` (not exported); the `json_*` names stay the ones of Jansson (libauth uses them). `test/json/safety.c` covers it; `json_tests_seed ()` runs first so the seed race is seen by TSan. `cerver/config.h` includes `<stdarg.h>`: its old `va_copy` with `memcpy ()` broke the json pack / unpack of clang in x86-64.
- Hot objects (2.0b-68): `http/core/recycle.{h,c}` keeps a cache per thread (and shared `FreeList`s) of `HttpResponse` and of buffers in power of 2 classes (2^8 to 2^16), the pattern of `packets.c`; nothing is recycled with `CERVER_RECYCLE_DISABLED` (the sanitizer builds). `http_response_delete ()` recycles the response, its header is written in its `header_buffer` when it fits (never `free ()` `response->header` directly), and its 64 headers are only cleared when `n_headers` says they were used. The body `String` of a request lives in its arena with a recycled buffer (`max_len` is the class size), and the file stats of a request too. `performance.sh` expects GET 0 and POST JSON 14 allocations (the 14 are the handler's `json_loads ()`).

## Conventions

- Code style: tabs, a space before call parentheses (`foo (bar)`) in every file, vendored code included, `#pragma region` blocks to group sections. Exceptions: a function-like macro name in its `#define NAME(x)` can not have a space, and the X-macro tables keep their existing form (`XX(...)` entries, `*_MAP(XX)` inside functions); X-macro arguments are stringified with `#`, so their text must not be changed.
- No literal values inside functions: sizes, lengths, prefixes, separators and timeouts are named constants (`#define` in the header or a `static const` at the top of the source file), e.g. `HTTP_ERROR_BUFFER_SIZE` instead of `char error_buffer[64]`. Applied to new code now; the rest of the codebase is migrated later.
- Keep `if` / `case` bodies short: when a branch needs its own variables or more than a couple of statements, move it to a dedicated `static` function and call it from the branch. Applied to new code now; the rest of the codebase is migrated later.
- Source files have a one-word name (`tree.c`, `compatibility.c`), never `route_compat.c`.
- `CHANGELOG.md` holds only the current version's changes, grouped under headings (`## HTTP`, `## Tests`, …), one line per commit message.
- Version bumps are a dedicated commit ("Updated version to Beta 3.0b-N") that updates `version.txt`, `include/cerver/version.h` (version, name, date, time), `ARG CERVER_VERSION` in `Dockerfile`, `cerver-install.sh`, and replaces `CHANGELOG.md` with that version's commit messages. `version.txt` and `CERVER_VERSION` must match or the version CI check fails.
- `docs/` is a git submodule (`ermiry/cerver-docs`).

## Branches

- `labs` is the 3.0 line, planned phase by phase in `roadmap.md` (L0 to L9): the JSON, the JWT, the parser, the I/O over io_uring, the API of the applications, SHA and deflate, HTTP/2, TLS and WebSocket, all of them of its own. It can break the API, the ABI and the architecture for a better design (each break in `incompatibilities.md`); its betas go to `labs-beta` as 3.0b-N ("Labs Beta"). The 3.0 goes to `master` only when it reaches the goal of `roadmap.md` §2, after the 2.1.
- `nightly` / `nightly-beta` is the experimental 2.1 line, `http` / `http-beta` the stable 2.0 line, `core` / `beta` the 1.x line. Nothing is merged between `labs` and them: at the start of each beta of `labs`, the fixes that `nightly` published are ported by hand into the code that `labs` still shares with it, and a module of `labs` that matures (it passes the gate of `labs` and loses no metric against the one that it replaces) can be ported by hand to `nightly`.
- The gate of a `labs` beta is the one of `nightly` plus the differential fuzzing, the conformance suites and the mutants of its modules, the faults of `test/faults/` and the benchmarks against the competitors (`roadmap.md` §6).
